# Members hub step 1, T1: D6 feasibility (run as the object's owner)

**Verdict: D6 is feasible as spec Part 4 describes it. No item rules it out.** P12 (a) (transient, inside the apply transaction) works on PG17, **but not in the form the plan words it**: `GRANT X TO <owner> WITH INHERIT FALSE, SET TRUE` … `REVOKE SET OPTION FOR X FROM <owner>` permanently strips the owner's own INHERIT and SET on every role it created (the common case, see item 1). T5 must use the corrected sequence in "Rulings for T4/T5" below. Two further findings change T5's verify (item 8: `neon_superuser` as grantor, per-column warnings).

- Compute: PostgreSQL **17.11** (`server_version_num` 170011), the stack `members-hub`'s pinned image.
- Probe: `services/worker/tests/d6_feasibility_live.rs` (`d6_feasibility`), one fresh database, the owner logged in directly as `postgres` over TLS (the orchestrator's path; a `cloud_admin` session under `SET ROLE` would hide every refusal, since a superuser session may `SET ROLE` anywhere). Every fact below is an assertion in that file.
- Run: `just workbench test -p worker --test d6_feasibility_live -- --run-ignored only`, 1 passed.
- Notation: the owner's rows in `pg_auth_members` for role X, `grantor:admin/inherit/set` (`boot` = bootstrap superuser, OID 10).

## Background fact that the plan missed

The owner carries `createrole_self_grant = 'set, inherit'`. So every role the owner creates, including every API-made role (`create_role_sql` runs `SET ROLE postgres; CREATE ROLE …`), gets **two** owner rows: `boot:true/false/false` (ADMIN) and `postgres:false/true/true` (INHERIT and SET, granted by the owner itself). The owner may already `SET ROLE` into them. The plan's "the owner holds ADMIN, `INHERIT FALSE, SET FALSE`" describes only the first row (and what the resync's repair at `services/worker/src/resync.rs:788-797` restores when the ADMIN row is missing).

## Rulings for T4/T5

1. **Run-as sequence (T5, replaces P12 (a)'s wording).** For each distinct `run_as` role X in an owner run, inside the apply transaction, with `owner` = the database owner:
   - if `pg_has_role(owner, X, 'SET')`: `SET LOCAL ROLE X` … `RESET ROLE`; **no grant** (the usual case: every API-made and owner-made role carries the createrole_self_grant row);
   - else if a `pg_auth_members` row (roleid X, member owner, grantor owner) exists: `GRANT X TO owner WITH SET TRUE` … `RESET ROLE; REVOKE SET OPTION FOR X FROM owner` (restores that row exactly; never name INHERIT);
   - else (ADMIN only, or ADMIN through an inherited membership): `GRANT X TO owner WITH INHERIT FALSE, SET TRUE` … `RESET ROLE; REVOKE X FROM owner` (leaves nothing);
   - else 422 (`extra.owner`).
   Hardening: T5 reads X's rows for the owner before the grant and compares them after the revoke, rolling back on any difference (fail closed). Cost if wrong: a standing membership of the owner changes.
2. **`owner_settable` (T5, in `privileges_sql.sql`):** with `o` = the object's owner, `o = current_user OR pg_has_role(current_user, o, 'SET') OR pg_has_role(current_user, o, 'MEMBER WITH ADMIN OPTION')` (the read runs on the database owner's connection, so `current_user` is the database owner). The plan's direct-row predicate is correct for the direct cases and greys an inherited-ADMIN owner that would work.
3. **`ALTER DEFAULT PRIVILEGES` (T4 as pinned):** `run_as = for_role` whenever `for_role` ≠ the session role; the statement then names the current role and needs SET only. Running it as the owner would need INHERIT.
4. **Grantor in verify (T5):** grants under `run_as X` are recorded as X's. An entry granted by `neon_superuser` (any `cloud_admin`-made table or sequence after the owner granted on it without SET ROLE, e.g. from the SQL editor) can't be revoked under `SET ROLE X`; only the owner without SET ROLE (or `GRANTED BY neon_superuser`) reaches it. The verify will report it as `still_granted_by: "neon_superuser"`. **Coordinator decision:** whether the privilege editor revokes `neon_superuser`-granted entries (as the owner, no `run_as`) or only reports them.
5. **Warnings (T5):** match `01006`/`01007` by `DbError::code()`; one `REVOKE` yields up to 1 + columns warnings, so count statements, not warnings.
