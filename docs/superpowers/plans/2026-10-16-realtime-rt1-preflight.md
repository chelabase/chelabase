### `chelabase_keys` output (`chelabase_keys.c`)
- `{"v":1,"lsn":"X/Y","xid":<u64>,"changes":[…]}` or `{"v":1,"lsn":…,"xid":…,"all":true}`; key order fixed `v, lsn, xid, changes|all` (`ck_commit_txn`). `lsn` = `txn->end_lsn` (`%X/%X`). `xid` = full 64-bit id, `FullTransactionIdFromAllowableAt(ReadNextFullTransactionId(), txn->xid)` (comparable with `pg_current_xact_id()`/`xid8`).
- Change: `{"rel":<oid>,"s":"<schema>","t":"<table>","op":"i"|"u"|"d","k":[[…],…]}` or `…,"op":"c"}`. Relations in first-change order; ops in order i, u, d (or one c); keys first-seen order, once per (relation, op); a key may be under both i and d. `rel` is the partition's own OID.
- Keys: JSON array of JSON strings per row (each column's type output function, then `escape_json`), converted to **UTF-8**; PK index column order (`indkey`). Keys only for `relreplident` `d` with a PK or `i` on the PK index; else `c`. NULL/dropped key column, missing tuple → `c`. Update: old key logged → equal texts `u`, different `d`+`i`; unchanged TOASTed new key column filled from the old key. TRUNCATE → `c` per relation. Non-row change actions → `c`.
- Options (`ck_startup`): `max_keys_per_table` 1–10000 (default 1000), `max_tables` 1–1000 (256), **`max_message_bytes` 65536–16777216 (1048576)**; decimal digits only, each at most once, unknown name → `ERROR 22023 chelabase_keys: unknown option "…"`.
- Bounds: `max_keys_per_table` counts a relation's **distinct keys across all ops**; exceeded → that relation `c`. `max_tables` exceeded, or the budget exceeds `max_message_bytes` → `all`. The budget counts message text **plus `KEY_MEMORY_OVERHEAD` per listed key** (hash element, KeyEntry, list cell, chunk header), so `all` comes before the text alone reaches the limit.
- Fixed settings, set once per transaction in `begin_cb`, popped in `commit_cb`: `DateStyle 'ISO, YMD'`, `TimeZone 'UTC'`, `IntervalStyle 'iso_8601'`, `extra_float_digits 3`, `bytea_output 'hex'`, **`lc_monetary 'C'`, `search_path ''`**.
- **SQL_ASCII database → `ERROR` at plugin startup** (slot creation and every start).
- No stream/prepare/message callbacks; transactions without row changes emit nothing; catalog changes not emitted.
- **No `schema_version` handling in the plugin.** `chelabase.schema_version` is an ordinary table (`one boolean PRIMARY KEY DEFAULT true CHECK (one), version uuid`, `services/worker/src/data_api.rs:330`, bumped by `UPDATE` in `bump_schema_version()` `:339-341`, event triggers `:391-392`), so a DDL in a data-API database arrives as `{"s":"chelabase","t":"schema_version","op":"u","k":[["t"]]}` in the DDL transaction's message; databases without the data API have no such table.

### Spec-vs-shipped differences (spec §3.1/§3.2, R1, R2, R6, R7)
1. `xid` (64-bit, `xid8` form) and key order `v,lsn,xid` — §3.1's example lacks `xid` (R7 asked for it). `lsn` is the commit's `end_lsn`.
2. Third option `max_message_bytes` (default 1 MiB) collapsing to `all`, budget including per-key memory overhead; option ranges 1–10000 / 1–1000; strict digits, given once.
3. `max_keys_per_table` is distinct keys per relation across all ops, not per op.
4. Fixed settings add `lc_monetary 'C'` and `search_path ''` to R6's five; the check preamble must set all seven.
5. All strings UTF-8; **SQL_ASCII databases refused** by the plugin (a slot can't be created there).
6. `schema_version` changes come as a normal `u` change on `chelabase.schema_version` (data-API databases only); R2's detection is realtime's job (by `s`/`t` or the relation OID).
7. Startup-packet rule (only `client_encoding`, `application_name`) — not in R1.
8. `IDENTIFY_SYSTEM` allowed; `SNAPSHOT` limited to `nothing`/`export`; one slot per session; names `rt_…` (spec §3.3 says `rt_<random>`: compatible) and reserved for the role.
9. HS feedback ignored on logical slots; client walsenders never synchronous standbys (not in the TE-RT spec).
