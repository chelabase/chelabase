# TE-A: the table API (implementation plan)

**Goal:** typed management endpoints for Studio's table editor: object list, table structure, type catalog, DDL and enum changes through one `schema-changes` endpoint (dry run, hash-confirmed cascade, opt-in `CONCURRENTLY`), an all-defaults insert and a full-cell fetch; a Postgres-side DDL guard for Developers on protected branches; the regenerated client and docs.

**Spec:** `docs/superpowers/specs/2026-10-13-table-api-design.md` (approved 2026-10-13). Implementers read the spec section their task names.

**Architecture:** API types in `chelabase_types::table_api` (serde, `openapi` feature for `ToSchema`); a pure renderer `chelabase_schema::ddl` built on the merge planner's renderers (`plan::ddl`, made `pub(crate)`); scoped catalog reads in `chelabase_schema::catalog`; orchestrator handlers in a new `services/orchestrator/src/table_api/` module reusing the SQL editor's session (`open_session`); the guard in the worker's member-roles reconciler.

**Tech:** Rust (axum, utoipa 6.0.0, tokio-postgres, sqlx in tests, pg_query 6.2.1, proptest 1.11.0 — added to chelabase-schema's dev-dependencies). No new dependency versions. No fork change: no image build; the live pass runs on the pinned images.

**Standing rule (2026-10-13):** the coordinator writes and commits each task's RED tests (below) before the brief, runs them RED and records it in the Status. Implementers make them pass without editing, weakening, skipping or deleting them; reviewers check `git diff <red-commit>..HEAD -- <test files>` is empty. Where a RED commit needs a module to exist so its tests compile, the coordinator adds only the empty module declaration (`pub mod x;` + `#[cfg(test)] mod tests;`), nothing else.

## Plan rulings (mechanical, listed for the user)

- **P1** The spec's `set_data_api_exposure` operation is dropped: the data API has no exposure flag; a table is reachable when `anon`/`authenticated` hold privileges on it (`chelabase-query/src/schema.rs`). Exposure is ordinary `grant`/`revoke`; the object list's `data_api_exposed` = `anon` or `authenticated` holds any table privilege and `USAGE` on the schema. Cost if wrong: one more operation later.
- **P2** The table structure response is the merge model's `Table` itself (it gains `ToSchema` behind a new `openapi` feature on chelabase-schema); the spec's per-column `type_ref` is dropped since every column already carries `type_oid` and the type catalog lists oids. Only ordinary tables are returned (the model's `tabs` rules); anything else is 404, and the object list's `editable` says why. Cost: TE-B joins by oid.
- **P3** Data types are structured (`TypeSpec { schema, name, modifiers, array }`) and rendered fully quoted (`pg_catalog."varchar"(200)`), never as SQL text; the type catalog hands back `schema` + `name`. Expressions (defaults, checks, `USING`, predicates, policy clauses) stay SQL text (S4).
- **P4** Grants render one statement per privilege (and per column), as the merge planner's `grant_sql` does, so both stay one renderer.
- **P5** The guard is `ddl_command_end` + `sql_drop` event triggers (not `ddl_command_start`), so temporary objects stay allowed: a command is refused when any object it touched is outside a `pg_temp*` schema. Functions live in a new superuser-owned schema `chelabase_guard` (PUBLIC has no USAGE), added to the merge exclusions and the data API's reserved schemas; not in `chelabase`, whose tamper check would quarantine it in databases that later enable the data API.
- **P6** The guard is installed by the member-roles reconciler on every reconcile of a **protected** branch, in every Postgres database it lists (`catalog.databases`), instead of joining the data API round-robin health check (that only covers served databases). The periodic sweep reconciles every branch, so a database created later gets it within one sweep. Protect/unprotect enqueues a reconcile.
- **P7** The marker role grant is its own reconciler step (`Lock`/`Unlock`), granted `WITH INHERIT FALSE, SET FALSE, ADMIN FALSE`, created on first use; `grantable()`'s refusal of `chelabase_*` stays for the normal grant path.
- **P8** Failure classification shared by the change and row endpoints, in `chelabase_types::table_api::classify_failure`: guard hint → 409 `branch_protected`; 42501 → 403 `permission_denied`; 55P03 → 409 `lock_timeout`; 57014 → 504 `timeout`; 23505/23503/23P01 → 409 `conflict`; 23502/23514/22xxx → 400 `constraint_violation`; anything else → 400 `schema_change_failed`.
- **P10** A dry run that hits a Postgres error answers with the same typed error as the real run (plus `dry_run: true`), not a 200 with `would_succeed: false`. Cost if wrong: TE-B shows dry-run failures as errors rather than as a "would fail" state.
- **P9** The dry-run size check is a pure function (`ddl::dry_run_plan`), unit-tested; the live tests don't exercise the threshold. The setting is `CHELABASE_TABLE_API_DRY_RUN_MAX_BYTES` (default 268435456).

**Behaviour:** spec §3 for the table, column and constraint operations, exactly the SQL below. Statement order inside `create_table`: `CREATE TABLE` (columns, then `PRIMARY KEY (…)`, then the constraints in request order), table comment, column comments (column order), RLS enable, RLS force, policies, grants (per privilege, per column), owner last. `alter_column` emits, in this order, `DROP DEFAULT` (only when both the type and the default change: `USING` isn't applied to the old default), `DROP IDENTITY`, type (with `COLLATE` and `USING`), the default (`SET DEFAULT`, or `DROP DEFAULT` unless already emitted), not-null, `ADD GENERATED … AS IDENTITY` / `SET GENERATED …`, comment, so Postgres accepts identity changes (an identity column refuses `SET DEFAULT` and `DROP NOT NULL`; `ADD … AS IDENTITY` needs NOT NULL first); only the `TYPE` statement may have `rewrites_table`, and every statement but the comment is `AccessExclusive`; an empty change is `Empty("change")`; `using` or `collation` without `data_type` is `Unsupported("using or collation without a type")`. `create_table` with no columns is `Empty("columns")`; a constraint with no columns is `Empty("columns")`. `rewrites_table`: `add_column` → true when its type's schema isn't `pg_catalog` (it may be a domain with constraints, which Postgres checks by rewriting, whatever the default), when it has `identity` or `generated`, or a `default` that isn't a plain literal (`-?[0-9]+(\.[0-9]+)?`, a single-quoted string with no cast, `true`, `false`, `null`, any case); `alter_column` with `data_type` → see T3's table (T2 may return `true` for every type change; T3 refines); everything else false. ## T3: renderer, the rest (opus / opus)

**Files:** `crates/chelabase-schema/src/ddl/*`, `Cargo.toml` (`proptest`), `tests/ddl_objects.rs` (coordinator), `src/ddl/tests.rs` (coordinator appends).

**Behaviour:** the remaining operations' SQL (below); the full lock table; `rewrites_table` for type changes (table below); `context_tables`, `dry_run_plan`, `dependents_sql`/`parse_dependents`/`dependents_hash`, `lock_sql`. `dry_run_plan`: a statement is skipped `Concurrently` when `concurrently`; `LargeTableRewrite` when `rewrites_table` and its table's `total_bytes` (from `ctx`; unknown = 0) is over `max_bytes`; every statement after the first `LargeTableRewrite` is `AfterSkipped`; others `None`. `dependents_sql`: one `jsonb` text row, the array of every object `DROP … CASCADE` of the request's drop targets would remove beyond the targets themselves and their own parts (columns, indexes, constraints, sequences owned by the target, the table's row type): views, materialized views, foreign keys of other tables, policies and indexes naming a dropped column, functions and columns of other tables of a dropped enum type; each `{kind, schema, name, parent, description}` with `kind` from `pg_identify_object`'s `type` and `description` from `pg_describe_object` (the text of Postgres's `drop cascades to …` notices; the hash covers it). Recursive through `pg_depend` (`deptype` `n`), `pg_identify_object` for the fields. A target the catalog doesn't have raises an error instead of an empty list. Accepted deviation (T3 review): dependents are `deptype 'n'` objects only; auto-dropped parts (an index or a generated column on a dropped column) aren't listed, as Postgres's own notices don't list them. Stale catalog knowledge (T3 review): the context and the dependents query describe the catalog before the request, so `render` refuses a `drop_table`/`drop_column`/`drop_enum` whose target (a column's table too) an earlier operation created, renamed (old or new name), moved (old or new), retyped or dropped (`DdlErrorKind::ChangedEarlier { by }`, the first such operation), and an `alter_column` type change on a column whose table or column an earlier operation changed counts as `rewrites_table`; nothing else is refused for this reason. `drop_enum` locks `AccessExclusive` with cascade (it drops columns of that type), `None` without. `dependents_hash`: SHA-256 hex of `serde_json::to_string` of the sorted list.

**Type-change rewrites** (`ctx` column `data_type` is `format_type` text): no rewrite for `character varying(n)` → `varchar(m≥n)` or `varchar` or `text`; `text` → `varchar` (no modifier); `numeric(p,s)` → `numeric(p2≥p,s)` or `numeric` (no modifier); every other change, any `using`, a column or table not in `ctx`: rewrite.

**Behaviour:** spec §3–4 with P8–P9. Order of a request:
1. Validate before any compute: `operations` non-empty (`invalid_request`), `lock_timeout_ms` in 1..=60000, `invalid_role`, `cascade.dependents_hash` 64 lowercase hex chars, `ddl::render` with an empty context (its `DdlError` → 400 `invalid_request` with `op_index` and the error text).
2. `load_authorized` with `APPLY_SCHEMA_CHANGES.policy.access` (`ActAsBranch`) and `Target::Role`.
3. `open_session` (owner or member login), then on that connection: read `context_tables`' models (`table_sql`) and sizes (`pg_total_relation_size`), re-render with the real context and `cascade`.
4. Not `concurrently`: `BEGIN`; `SET LOCAL lock_timeout`, `SET LOCAL statement_timeout` (dry run 15 s, real 60 s); `SET LOCAL ROLE` when acting as a role; if the request has drops: `lock_sql`, then `dependents_sql` → `dependents`; on a real run with `cascade` and a hash that differs → `ROLLBACK`, 409 `dependents_changed` with `dependents` in the extra; then each statement (dry run: only those `dry_run_plan` says to run), collecting notices; after a cascading drop runs, its `drop cascades to …` notice lines (the NOTICE's DETAIL, one per object, or the `drop cascades to <desc>` message for a single one) must equal the confirmed dependents' `description`s as a set, else `ROLLBACK` and 409 `dependents_changed` (a notice reporting more objects than it lists, "and N other objects", counts as a mismatch unless N matches); dry run `ROLLBACK`, real run `COMMIT`. A Postgres error → `ROLLBACK`, `classify_failure` with extras `op_index`, `sqlstate`, `message`, `detail`, `hint`, `position`.
5. `concurrently`: dry run: no execution (`skipped: concurrently`), after checking the table exists via the context read (404 `not_found` if not). Real run: no transaction; `SET lock_timeout`, `SET statement_timeout` (900 s for index builds), `SET ROLE`; the statement; on failure, as the owner, `DROP INDEX IF EXISTS <qualified>` when `pg_index.indisvalid` is false for that name, then 409 `index_build_failed` with the Postgres fields.
6. The response `SchemaChangeResponse`; `would_succeed` = `Some(true)` when every statement ran and the dry run hit no error, `None` when any was skipped. A dry run that hits a Postgres error returns the same typed error as the real run (status and code), with `dry_run: true` in the extras (P10), so `would_succeed` is never `Some(false)` in a 200.
7. Audit: one `info` line `schema change` with user, branch, database, role, op count, dry_run, committed (no SQL, no values).
