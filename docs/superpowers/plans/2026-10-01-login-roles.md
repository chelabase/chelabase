# Login Roles: Implementation Plan (roadmap step 6a)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** extra login roles per branch (plain or owner-level), managed through the platform API and Studio, that log in through Neon's proxy.

**Architecture:**
- A login role is a `neon_roles` row (kind `login`) with a SCRAM verifier and a sealed password. The row goes into the compute spec, so `compute_ctl` creates the role at start and on every reconfigure; the fork's `privileged: false` makes it plain.
- The worker owns create, reset and delete (NATS RPCs) under the endpoint lock; delete drops the role through `admin_sql`. After every apply that touches a plain role, the worker checks that the role really is plain and demotes it otherwise.
- The orchestrator serves the list from metadata, forwards writes to the worker, and reveals a role's connection details with `?role=`.

**Tech stack:** Rust 2024 (axum 0.8.9, sqlx 0.9.0, tokio, async-nats 0.50.0), Postgres 17.5 on the ChelaDB Neon fork's compute image, utoipa 6.0.0 + utoipa-axum 0.3.0 (documents in `openapi/`), orval 8.38.0 (`@cheladb/management-client`), React Studio on TanStack Query 5.104.0 (vitest).

**Spec:** `docs/superpowers/specs/2026-10-01-login-roles-design.md`. Executors read both. The spec wins on behaviour; this plan wins on names and interfaces, and on the rulings listed under Status.

## Review Focus

1. **Concurrent writes on one endpoint.** Two creates racing the cap (only one passes at the limit), and a reset of role A while role B's apply is in flight: neither change is lost, and the flag clears only when everything stored has been applied. Tested in Task 1 (cap under concurrent inserts, live metadata) and Task 3 (a write between the apply's read and its clear leaves the flag set).
2. **A role that exists in SQL but has no row**, created by the owner in SQL, or left by a parent branch's later delete: create answers 409 `role_exists` and adopts nothing. Tested in Task 3 (fake `pg_roles` hit) and Task 6 live.
3. **An image that ignores `privileged`** (or a role made owner-level by hand): the check demotes it, logs ERROR, and create answers 500 `role_privilege_mismatch`. Tested in Task 3 (fakes) and Task 6 live (`ALTER ROLE … CREATEROLE` by hand, then reconcile's check demotes).
4. **Delete with objects and sessions in several databases,** including one made with `CREATE DATABASE` in SQL: the objects end up owned by `postgres`, open sessions end, the login is refused at once, and a retry after a mid-way failure succeeds. Tested in Task 4 (SQL order over every database) and Task 6 live.
5. **Hostile or edge names:** `Admin` (uppercase), `a-b`, 64 bytes, `pg_x`, `PG_x`, `public`, the owner's name, an empty name: all 422 before any worker call; 63 bytes is fine. Tested in Task 1 (the name check) and Task 5 (routes answer 422 without an RPC).
