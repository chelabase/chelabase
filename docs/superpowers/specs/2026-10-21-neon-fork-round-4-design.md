## Decisions

User (2026-10-21):
- **D1** Personal-login guard by a role marker: the neon extension registers a superuser-only setting `chelabase.managed_role` (`PGC_SUSET`); the worker creates a personal login and, in the same transaction as `cloud_admin`, runs `ALTER ROLE x SET chelabase.managed_role = 'personal'`; round 3's managed-role guard also refuses every role statement it covers on a role carrying the marker, for any name. `cb_m_*` and `chelabase_realtime` keep their name rules. Personal logins stay on the normal proxy path.
- **D2** compute_ctl's internal server `:3081` binds loopback (127.0.0.1 and ::1) **and** requires a per-start random secret, handed to the neon extension through a hidden superuser-only GUC written in `postgresql.conf`; the extension's curl callers send it as a bearer. Works on Kubernetes (same pod) as on Docker.
- **D3** JWT auth on the pageserver's and safekeepers' `/profile/cpu`, `/profile/heap` (admin scope) and `/metrics`, with a new read-only `metrics` scope that opens metrics and nothing else.

Coordinator rulings given with the items:
- **Item 7:** the tenant storage token moves from the `NEON_AUTH_TOKEN` environment variable to a hidden superuser-only reloadable (`PGC_SIGHUP`) GUC; a refresh arrives through compute_ctl's `/configure`; compute_ctl rewrites the config and reloads; every new pageserver/safekeeper connection reads the current value.
- **Item 9 (W31):** mirror round 3's member-login block for `chelabase_realtime`: a CIDR list plus `clientcert=verify-full`, its own CN `chelabase-realtime` in `pg_ident.conf`, reject lines for the role everywhere else; realtime's client certificate comes from the platform CA the orchestrator's comes from.

Also in this round (RT1's list): U16 (item 1), W9 (item 2), compute_ctl `:3080`'s 400 (item 4), the `tenant_id.unwrap()` panic (item 5), the proxy's Valkey password on argv (item 8), storcon's retry without backoff (item 10).

User answers to the first draft's open questions (2026-10-21; they **supersede D2's and item 7's GUC wording**):
- **U1 Token files, not GUCs**, for both the `:3081` secret (D2) and the storage token (item 7). compute_ctl writes each to a 0600 file outside pgdata, owned by the postgres OS user, replaced atomically (temporary file plus rename) on refresh. The neon extension caches the value in memory and re-reads it when the file changes (one `stat()` per new pageserver/safekeeper connection or per `:3081` call; never per query or page). No GUC, no reload, nothing logged. The file is the one mechanism for every caller (neon extension, local_proxy, the proxy's testing `Local` backend, the Python fixtures).
- **U2** The `metrics` token is long-lived and never expires, metrics-only, minted by Chelabase into `.chelabase/` (re-minted to rotate); scrapers use it as a `bearer_token_file`. It opens `/metrics` on the pageserver, the safekeepers and the storage controller.
- **U3** Startup GUC options (`options=-c …` and other startup-packet settings) are refused for `chelabase_realtime` logins, so the `logical_decoding_work_mem` role setting can't be overridden. (Already in the fork: §3.)
- **U4** compute_ctl `:3080`'s `/metrics` and `/autoscaling_metrics` go behind its JWT with the same `metrics` scope (§7).

**Why not GUCs** (the first draft's finding that led to U1):
1. `GUC_SUPERUSER_ONLY` doesn't hide a value from the database owner. `ConfigOptionIsVisible` lets any role with the privileges of `pg_read_all_settings` read it (`src/backend/utils/misc/guc_funcs.c:581-588`), `SHOW`/`current_setting()` check only that (`guc.c:4367-4372`, `:5452-5457`), and compute_ctl's migration 0004 grants `pg_monitor` (which contains `pg_read_all_settings`) to `neon_superuser` (`compute_tools/src/migrations/0004-grant_pg_monitor_to_privileged_role.sql`), whose member every spec role is (`compute_tools/src/spec_apply.rs:1304`, `CREATE ROLE … IN ROLE neon_superuser`). `GUC_NO_SHOW_ALL` only drops it from `pg_settings` and `SHOW ALL` (`guc_funcs.c:946-951`).
2. A `PGC_SIGHUP` reload logs every changed value from the postmaster: `parameter "%s" changed to "%s"` (`guc.c:545-572`), so a refreshed token would be written to the compute log at every refresh.

## 2. Item 1 (U16): a temporary slot's `neon-file:` copy outlives a restart

**Today.**
- `SaveSlotToPath` sends the slot's on-disk state to the pageserver as a `neon-file:pg_replslot/<slot>/state` logical message for **every** logical slot with a valid `restart_lsn`, whatever its persistency (`slot.c:2145-2156`). `CreateSlotOnDisk` (`:2022-2057`), `ReplicationSlotSave` (`:1048-1055`) and every checkpoint (`CheckPointReplicationSlots`, `:1904-1951`) call it, so a temporary `rt_` slot is copied at its first checkpoint.
- `ReplicationSlotDropPtr` logs the removal (an empty `neon-file:` message) for every logical slot it drops (`:948-955`); a temporary slot's normal end goes through it.
- After a crash or `restart_after_crash = off` exit, the next compute's basebackup ships the state (`pageserver/src/basebackup.rs:483-509`); `RestoreSlotFromDisk` deletes a non-persistent slot's directory without logging anything (`slot.c:2391-2401`; WAL can't be written there: `StartupReplicationSlots` runs at `xlog.c:5679`, WAL inserts are allowed from `:6237`). The aux entry stays on the timeline for good and is inherited by every child branch made after it.
- The basebackup also folds each `pg_replslot` entry's `restart_lsn` into `restart.lsn` (`basebackup.rs:486-527`). No code in this tree reads `restart.lsn` (grep over `pgxn/`, `compute_tools/`, `vendor/postgres-v17/src`), so the harm is the stale entries themselves: shipped to every start, deleted locally each time, carried into children, and counted in `restart.lsn` and the aux size estimator. The slice `content[offs..offs + 8]` (`:491-493`) also panics on a state shorter than 96 bytes.
- The pageserver logs `warn!` for a removal of an aux file it doesn't have (`pageserver/src/pgdatadir_mapping.rs:2795`).

**Rule.**
1. **No copy for non-persistent slots** (Postgres fork): `SaveSlotToPath` sends the `neon-file:` message only when `cp.slotdata.persistency == RS_PERSISTENT` (temporary and ephemeral slots never reach the pageserver). `ReplicationSlotPersist` (`:1083-1096`) saves after setting `RS_PERSISTENT`, so a persistent slot is still copied once its creation succeeds.
2. **Drop logs only what was copied:** `ReplicationSlotDropPtr` logs the removal only for `RS_PERSISTENT` logical slots (a temporary slot never had a copy; logging it would trip the pageserver's `warn!`).
3. **Existing stale entries are removed at start** (Postgres fork): `RestoreSlotFromDisk`, when it deletes a non-persistent slot, records the slot name in a list kept in the startup process (it is the process that later runs `StartupXLOG`'s end-of-recovery steps). A new `LogDiscardedSlotFiles()` (slot.c, declared in `slot.h`) runs in `StartupXLOG` right after `XLogReportParameters()` (`xlog.c:6264`, local WAL inserts on since `:6237`) and logs one removal message `neon-file:pg_replslot/<name>/state` per recorded name, then flushes. Only a primary: in a standby the list is dropped (a replica's basebackup ships no `pg_replslot`, `basebackup.rs:487-489`). Idempotent: a compute that dies before the flush cleans up at its next start.
4. **Basebackup** (Neon fork, all majors): a `pg_replslot/*/state` entry is still shipped (rule 3 needs to see it), but only entries whose persistency field (offset 84 of `ReplicationSlotOnDisk`, `RS_PERSISTENT = 0`, `slot.h:35-37`) is `RS_PERSISTENT` count towards `restart.lsn`; an entry shorter than the offsets it reads is skipped with a warning, never a panic. A new `pg_constants::REPL_SLOT_ON_DISK_OFFSETOF_PERSISTENCY`.
5. v14–v16 keep their slot.c (S-ruling S1 of round 3 applies; "Not in this round").

**Tests.**
- Python (Neon suite, `neon_simple_env`), new `test_temp_slot_aux_files.py`, using `PageserverHttpClient.list_aux_files` and `ingest_aux_files` (`test_runner/fixtures/pageserver/http.py:1206-1225`):
  - a temporary logical slot held across a `CHECKPOINT`: no `pg_replslot/<slot>/state` aux file; a persistent slot's appears, and goes when it is dropped;
  - a compute killed (`immediate` stop) while it holds a temporary `chelabase_keys` slot, then started: no aux entry for it, `pg_replication_slots` empty;
  - a stale non-persistent state seeded with `ingest_aux_files` (what an older compute left): after one start it is gone from `list_aux_files` at the new LSN, and the pageserver log has no `removing non-existing aux file`;
  - a child branch created from an LSN before the cleanup cleans its own copy at its first start;
  - the RED tests run on today's fork build and fail on their first assertion (the aux file is there).
- Rust unit (pageserver): the basebackup's slot-entry reading (a helper returning the restart LSN only for a persistent, long-enough state): persistent, temporary, ephemeral, 0 bytes, 95 bytes.
- Chelabase live (§13.3): `compute_fork_live::a_crashed_compute_leaves_no_slot_aux_file`.

## 3. Item 2 (W9): `chelabase_keys` streams large transactions

**Today.** The plugin sets no stream callbacks (`chelabase_keys.c:36-38`, `:183-191`), so `ctx->streaming` is false (`logical.c:313-319`) and a transaction above `logical_decoding_work_mem` spills to `pg_replslot/<slot>/` (`reorderbuffer.c:3783-3830`); every `rt_` slot decodes all WAL and spills on its own (RT1 red-team W9). RT1 sets `ALTER ROLE chelabase_realtime SET logical_decoding_work_mem = '8MB'` (`services/worker/src/realtime.rs:72`). A database walsender applies role settings: `InitPostgres` runs `process_settings(MyDatabaseId, GetSessionUserId())` for it (`postinit.c:1020-1039` returns early only for physical walsenders; `:1247`). RT1's `realtime_live::a_big_transaction_spills_through_the_rt_slot` (`services/realtime/tests/realtime_live.rs:1188-1218`) shows the setting took effect (a ~20 MB transaction spills, which 64 MB would not), but nothing in the fork tests it. **U3 is already in the fork:** round 3's T3 m1 refuses, for `chelabase_realtime`, every startup-packet setting but `client_encoding` and `application_name`, and any setting carried in `options` (`postinit.c:1286-1354`, `check_chelabase_realtime_startup`, called at `:1010-1011` before the settings are applied), with tests (`test_runner/regress/test_chelabase_realtime_role.py:496-537`, `logical_decoding_work_mem` as a startup key and through `-c`). This round adds no code for U3, only the walsender test below (the role setting itself takes effect).

**Rule (contract additions to round 3 §2; the output format is unchanged).**
- `_PG_output_plugin_init` also sets `stream_start_cb`, `stream_stop_cb`, `stream_abort_cb`, `stream_commit_cb`, `stream_change_cb` and `stream_truncate_cb` (the wrapper skips truncates silently without it, `logical.c:1698-1700`). No `stream_message_cb` (logical messages stay skipped), no `stream_prepare_cb` (no two-phase, so `ctx->twophase` stays false and a prepared transaction is decoded at `COMMIT PREPARED`).
- Streaming is always on (no option, S3): Postgres streams the largest top-level transaction once the slot's reorder buffer exceeds `logical_decoding_work_mem` (`reorderbuffer.c:3805-3818`), and still spills when the transaction can't be streamed yet (a partial TOAST or speculative change, `:3757-3759`; before the slot is consistent, `:4180-4193`).
- **A streamed transaction keeps no keys** (S4): `stream_change_cb` and `stream_truncate_cb` record only the relations it touched, per top-level xid, in first-change order, each with its prefix (`rel`, `s`, `t` from the historic catalog, as `get_rel` builds it). Past `max_tables` relations the transaction is `all` and collection stops. State lives in a per-xid entry of a hash in the plugin's context (bounded by `max_tables` relations per streamed transaction).
- `stream_commit_cb` writes the transaction's one message, in the same form and at the same place as a commit (`lsn` = `txn->end_lsn`, set before `ReorderBufferStreamCommit` at `reorderbuffer.c:2724-2739`; `xid` = the full xid as in round 3 RT3-2): `{"v":1,"lsn":…,"xid":…,"changes":[{"rel":…,"s":…,"t":…,"op":"c"},…]}` or `"all":true`. A streamed transaction that touched no rows writes nothing.
- `stream_abort_cb`: a top-level abort (`rbtxn_is_toptxn(txn)`) drops the entry and writes nothing; a subtransaction abort keeps the entry (a `c` for a relation only the aborted subtransaction touched is a harmless extra refetch). The implicit abort of a transaction that was in progress at a crash (`ReorderBufferAbortOld` → `stream_abort(…, InvalidXLogRecPtr)`, `reorderbuffer.c:3052-3053`) is a top-level abort too (RT4-13).
- The per-xid entry is freed on every end: `stream_commit`, every top-level `stream_abort`, and `ROLLBACK PREPARED`; the hash never grows across a long walsender session (RT4-13).
- `stream_start_cb`/`stream_stop_cb` write nothing. Stream callbacks print no keys, so they set no output settings (R6 applies to key text only).
- The non-streamed path is unchanged; streamed blocks never nest inside a commit replay (the memory check runs while queueing changes), so the two states don't mix.
- Realtime already treats `c` and `all` (W10: `all`, or any op on `chelabase.schema_version`, counts as a schema change), so no realtime code change; its test changes (§3 Chelabase).

## 4. Item 3 (D2): compute_ctl's internal server

**Today.** `Server::ip()` binds both servers to `[::]` (`compute_tools/src/http/server.rs:192-199`); the internal router has `/extension_server/{*filename}`, `/extensions`, `/grants` (runs `GRANT … ON SCHEMA` as compute_ctl's `cloud_admin` connection, `http/routes/grants.rs:14-47`), `/refresh_configuration` and, with `testing`, `/failpoints` (`server.rs:65-88`), all without auth. Anything that reaches the compute's port 3081 (another compute on the network, a sidecar, a SQL-reachable HTTP client) can use them. Callers: `extension_server.c:49-54` (`http://localhost:<neon.extension_server_port>`, no header), `libpagestore.c:1059-1083` (`refresh_configuration`, `http://localhost:…`, only in lakebase mode, `:1065-1066`), `local_proxy` (`--compute-ctl`, default `http://127.0.0.1:3081/`, `proxy/src/binary/local_proxy.rs:74`; `/grants`, `/extensions` through `proxy/src/compute_ctl/mod.rs`), the proxy's testing `Local` backend (`proxy/src/binary/proxy.rs:921-925`), and Neon's Python fixtures (`test_runner/fixtures/endpoint/http.py:161-208`: `/extensions`, `/grants`, `/failpoints`). `neon.extension_server_port` is written into `postgresql.conf` (`compute_tools/src/config.rs:432`). Chelabase never calls 3081 (`scripts/compute-network-e2e.sh:187-189` lists it as a known gap).

**Rule.**
- **Bind:** the internal server listens on `127.0.0.1:<port>` and, when the host has IPv6 loopback, `[::1]:<port>`; a failure to bind `::1` (Kubernetes pods without IPv6) is logged once and ignored, a failure to bind `127.0.0.1` stops compute_ctl as today. The external server is unchanged.
- **Secret:** at start compute_ctl draws 32 bytes from the OS RNG and hex-encodes them (64 characters); the value lives in `ComputeNode` for the process's life (a compute_ctl restart is a Postgres restart, so "per start").
- **Middleware** on every internal route: `Authorization: Bearer <secret>`, compared in constant time; missing, malformed, another scheme or a wrong value → `401` with `WWW-Authenticate: Bearer` and a JSON error that never echoes the header.
- **Delivery (U1):** compute_ctl writes the secret, before it starts Postgres, to the token file `--internal-api-token-file` (default `<pgdata parent>/compute_ctl_internal.token`, i.e. `/var/db/postgres/compute_ctl_internal.token` for Chelabase) by §4.1's rules. Every caller reads that file: `extension_server.c` and `libpagestore.c` through §4.1's cache (one `stat()` per `:3081` call); `local_proxy` through a new `--compute-ctl-token-file` and the proxy's testing `Local` backend through the same flag (read before each call, so a compute restart's new secret is picked up); the Python fixture reads its endpoint's file (S5).
- **Callers:** `extension_server.c` and `libpagestore.c` add the bearer header (a `curl_slist` freed after the call) and use `http://127.0.0.1:<port>` instead of `localhost` (no resolver step, works without IPv6). A missing, empty or invalid file means no header: the call is refused (fails closed) and logged once per change of the file's state, never with its content.

### 4.1 Token files (U1; shared with §8)

- **Writer (compute_ctl):** each token goes to its own file outside pgdata, mode 0600, owned by the postgres OS user compute_ctl runs as: written to `<file>.tmp.<pid>` (created `O_EXCL`, 0600), `fsync`ed, renamed over `<file>`, the directory `fsync`ed. Content: the token and one `\n`. Never logged.
- **Paths to Postgres:** compute_ctl writes the two paths (not the tokens) into `postgresql.conf` as `neon.compute_ctl_token_file` and `neon.storage_auth_token_file` (`PGC_POSTMASTER`, ordinary visible GUCs; a path isn't a secret), after the spec's `postgresql_conf` and `settings` so neither can redirect them (as `neon.branch_protected`, `config.rs:465-475`).
- **Reader (neon extension, `pgxn/neon/token_file.c`, S1):** a per-process cache `{path, st_dev, st_ino, st_size, st_mtim, value}`. Before each use (a new pageserver or safekeeper connection, a `:3081` call) one `stat()`; when device, inode, size or mtime differ from the cache (a rename always gives a new inode), the file is opened, read whole (at most 8 KiB) and validated: one line of `[A-Za-z0-9._~+/=-]`, 1–8191 bytes, the final `\n` stripped. Nothing is read per query or per page.
- **Fail closed:** a missing, unreadable, empty, oversized or invalid file gives no token (the connection is made without a password and the server refuses it; the `:3081` call goes without a header and is refused). The cache keeps no old value past a failed re-read. A `WARNING` names the path and the reason once per state change, never the content.
- **A refresh racing a connect:** the writer only renames complete files, so a reader opens either the old or the new inode and reads a whole token; both are valid (the old one has hours left, §8). A reader that `stat`s the old inode and opens after the rename reads the new one; the cache records the inode it actually read (`fstat` on the open descriptor).
- **No SQL path reads them (verified for the plan; the red-team re-checks):** the files are outside pgdata and every server-side file reader needs a privilege `neon_superuser` doesn't hold: `pg_read_file`, `pg_read_binary_file`, `pg_stat_file`, `pg_ls_dir` on absolute paths need `pg_read_server_files` (or superuser); `COPY … FROM '<file>'` needs `pg_read_server_files`, `COPY … FROM PROGRAM` `pg_execute_server_program`; server-side `lo_import` is superuser-only unless granted (no migration grants it; `lo_compat_privileges` stays off); `adminpack` is gone in PostgreSQL 17; `file_fdw` isn't marked trusted in the image (`compute/compute-node.Dockerfile:201-213`, the contrib trusted list), so only a superuser can create it. SQL-level privileges are necessary but not sufficient: a trusted C extension can open files itself (RT4-1). Settled by the red-team: Chelabase ships the `EXTENSIONS=minimal` image (`publish-dev.sh:228`, `infra/neon/README.md:49`; `extensions-minimal` is pgrag, timescaledb, pg_cron, pg_partman, `compute-node.Dockerfile:1653-1658`), in which nothing reads local files or reaches an arbitrary URL (pgrag calls fixed hosts). The platform variant `extensions-all` also ships `anon` (its loaders are `SECURITY INVOKER` `COPY FROM`, so they need `pg_read_server_files`: safe), `pg_duckdb` 0.3.1 (superusers only unless `duckdb.postgres_role` is set) and `pg_mooncake` 0.1.2, whose vendored pg_duckdb has its non-superuser and `disabled_filesystems` guards commented out: any role that can create it reads any file, and `neon.allow_unstable_extensions` (`PGC_USERSET`, `pgxn/neon/unstable_extensions.c:108-113`) lets an owner create it. **RT4-1 (user):** this round removes `pg_mooncake` from the image entirely (its Dockerfile layers, `duckdb_v113.patch`, `manifest.yaml`, its tests); bumps `pg_duckdb` to the latest release (v1.1.1 per the GitHub releases page on 2026-10-21; the plan pins the exact tag, its commit and the source checksum) with its superuser-only default (`duckdb.postgres_role` unset) and compute_ctl pinning `duckdb.disabled_filesystems = 'LocalFileSystem'` at postmaster level in `postgresql.conf` (after the spec's settings) on every compute; reworks or drops `pg_duckdb_v031.patch`, `duckdb_v120.patch` and the privileged-role grant workaround (`compute-node.Dockerfile:1515-1517`) for the new version; and makes `neon.allow_unstable_extensions` `PGC_SUSET`. `dblink`/`postgres_fdw` (trusted) connect to Postgres, not to files, and require a password for non-superusers. A superuser (`cloud_admin`, or the opt-in superuser owner) can read the files, as it can do anything.
- **The cache's identity (RT4-12):** two refreshes within one mtime tick still force a re-read (each rename gives a new inode); the identity recorded is the open descriptor's (`fstat` after `open`), never the pre-open `stat`, so a stat-old/open-new race can't cache the wrong identity; a re-read that finds a missing, empty, oversized or invalid file drops the cached value.
- **Kubernetes:** the files live in the compute container's own filesystem; nothing depends on Docker.
- **The secret is `cloud_admin`-grade (RT4-6):** whoever holds it acts through compute_ctl's `cloud_admin` connection. So the internal routes are narrowed to what their callers need, and a leaked secret is less than `cloud_admin`: `/grants` accepts only `USAGE` and `CREATE`, only on a schema owned by a non-superuser (never `pg_catalog`, `information_schema`, `pg_toast*` or a superuser-owned schema such as the platform's), and only for an existing grantee that isn't a superuser, `neon_superuser`, `cloud_admin`, a `pg_*` role or a Chelabase-managed role (round 3's names or §12's marker); `/extensions` installs only extensions whose control file is `trusted` (what the owner could install itself). Anything else → `403`, nothing run.
- **No bypass, no logging (RT4-10):** the internal middleware has no environment or instance switch (an `INSTANCE_ID` doesn't loosen it) and never logs the bearer or the secret.
- **Kubernetes:** compute_ctl and Postgres share the container, so loopback reaches them; other containers of the pod share loopback too and are kept out by the secret (only a container given the token file can call). Nothing depends on Docker.

## 11. Item 10: storcon retries serialization failures with backoff

**Today.** `with_conn` retries a `SerializationFailure` up to `MAX_RETRIES` = 128 times with no pause (`storage_controller/src/persistence.rs:169`, `:317-357`), so colliding transactions retry in lockstep and exhaust the budget within milliseconds (RT1's `rest_live` 500s). The migration loop's `SerializationFailure` arm (`:243-276`) can't match: every error there is already mapped to `DatabaseError::Migration` (`:251`).

**Rule (S14).** Full-jitter exponential backoff: before retry `n` (1-based) sleep a uniform random duration in `[0, min(500 ms, 10 ms × 2^(n-1))]`, with the pooled connection returned before the sleep; at most 20 retries (worst case about 8 s), then the error as today; the retry count is a histogram (`storage_controller_database_query_retries`). The migration loop's dead arm is removed (migrations run once at startup on one connection).

**Tests.** Rust unit: the delay function (bounds per `n`, cap, jitter spread with a seeded RNG); a fake transaction that fails `k` times with `40001` succeeds after `k` sleeps (paused tokio clock) and fails after 20. Python: `test_storage_controller.py::test_serialization_failures_back_off` (two concurrent bursts of shard generation increments; no request fails). Chelabase: `rest_live` in the end-of-step pass (no intermittent 500).

## 12. Item 11 (D1): the personal-login marker

**Today.** `CheckManagedRoleStatement` refuses, for a non-superuser current user, the role statements of round 3 §4.1 when they name a `cb_m_*` (any case) or `chelabase_realtime` role (`pgxn/neon/neon_ddl_handler.c:1775-1908`), called first in `NeonProcessUtility` (`:2172`). Postgres refuses non-superusers `ALTER ROLE … SET` of a `PGC_SUSET` parameter unless granted `SET` on it, which only a superuser can grant. `pg_db_role_setting` is a shared catalog, so a role setting is carried by branches. The extension already reads it for databases (`DatabaseBornClosed`, `:1964-2010`). `chelabase.*` can't be a reserved GUC prefix: Chelabase sets `chelabase.claims` and `chelabase.user_id` session variables.

**Rule (fork).**
- The extension defines `chelabase.managed_role` (string, `PGC_SUSET`, default empty, `GUC_NOT_IN_SAMPLE`). It has no runtime effect; it is a marker.
- **Marked role:** a role with a `pg_db_role_setting` row `(setdatabase = 0, setrole = <oid>)` whose `setconfig` holds a `chelabase.managed_role=` entry, whatever its value (S15: fails closed; the worker writes `personal`). A database-scoped setting doesn't mark.
- `CheckManagedRoleStatement` refuses (`42501`), for a non-superuser, every statement form of round 3 §4.1 when any role it names (resolved to an OID with `get_role_oid(name, true)`; a name that doesn't exist yet isn't marked) is marked: `CREATE ROLE`'s `IN ROLE`/`ROLE`/`ADMIN` lists, `ALTER ROLE`/`USER` (any option), `ALTER GROUP … ADD/DROP USER`, `ALTER ROLE … [IN DATABASE …] SET/RESET`, `RENAME` (old name), `DROP ROLE`, the grantees and granted roles of `GRANT`/`REVOKE` role. Message `role "%s" is managed by Chelabase` (the member/realtime message stays as it is, S16). `CURRENT_USER`/`CURRENT_ROLE`/`SESSION_USER` resolve as in round 3, so a personal login can't change its own password or settings from SQL.
- **The marker itself:** a non-superuser `ALTER ROLE <any> [IN DATABASE …] SET`/`RESET chelabase.managed_role` and `GRANT/REVOKE SET|ALTER SYSTEM ON PARAMETER chelabase.managed_role` are refused by the hook for any role, marked or not (Postgres refuses them too; the hook gives one message and covers a `SET` privilege granted by mistake). `RESET ALL` on an unmarked role is unaffected.
- **Creating a role that then gets marked:** only a superuser can mark, so a non-superuser can create a role but never mark it; the worker creates the personal login itself (`CREATE ROLE` fails if the name exists, so it never adopts a customer's role) and marks it in the same transaction, so no other session ever sees the role unmarked.
- Object privileges, ownership (`REASSIGN/DROP OWNED`), `COMMENT ON ROLE` and `SECURITY LABEL` stay outside the guard, as in round 3 §4.1 (S16).
- Superusers (`cloud_admin`; compute_ctl's migrations) are untouched; the marker lookup runs only when the current user isn't one.
- **The marker travels with the role (RT4-4):** a branch copies it with the catalog, but a role can also be made again by a path that isn't a copy: the resync recreates an API-made role "the compute lost" from its row (`services/worker/src/resync.rs:1-9`; it carries attributes, memberships and the password, no role settings), and compute_ctl's spec apply creates every spec role (`spec_apply.rs:1295-1306`). Contract, pinned now so the Members step builds on it: a personal login is recorded as such in the control plane (its role row's origin), **every** path that creates or recreates it runs the marker statement in the same transaction (the resync's recreate included), and personal logins are never compute-spec roles (which would also make them `neon_superuser` members). This round adds the worker helper and the resync's re-marking for a row recorded as personal; the Members step adds the rows.

**Chelabase (this round; the Members page builds personal logins on it).**
- `crates/chelabase-types/src/role_name.rs`: `pub const PERSONAL_LOGIN_MARKER: &str = "chelabase.managed_role"` and `pub fn mark_personal_login_sql(role: &str) -> String` (`ALTER ROLE <quote_ident> SET chelabase.managed_role = 'personal';`), plus `is_marked_sql()` (the catalog check used by tests and later by the role lists).

The shipped (`minimal`) image has no such extension. `pg_lake` is a later step.
- **RT4-2 (important, user; §8).** Capability gate instead of a deploy order: compute_ctl advertises `storage_token_refresh` (`/status` `capabilities`, and the `Compute-Capabilities` header of its spec fetch); expiring 24 h tokens go only to computes that advertise it, non-expiring to the rest until they restart on the new image. Rollback stays safe. (Supersedes the red-team's deploy-order proposal.)
- **RT4-3 (important; §8).** A refresh can't fail a running compute: it goes through a dedicated `POST /storage_token` that only writes the token file (no status change, no reload, no pgbouncer/local_proxy/rsyslog), not through `/configure`. This takes the red-team's option (a); with U1's files no reload is needed at all. The first draft's `skip_pg_catalog_updates` refresh is withdrawn.
- **RT4-4 (important; §12).** The marker travels on every path that makes a personal login again: the control plane records personal logins; every create or recreate (the resync's included) marks in the same transaction; personal logins are never compute-spec roles. *Partly disagreed:* the red-team's scenario (a role made on a parent after a child exists is "forwarded to the child") doesn't happen: branches don't share roles after the branch point, and resync works per branch. The real recreate paths are the resync's "a role the compute lost is made again" and compute_ctl's spec-role apply; the contract covers both, with a live test of a recreate.
- **RT4-5 (important; §7).** Metrics and profile handlers check membership in an allowed scope set on all three servers (storcon's equality-only `check_permission` isn't used for them); tables include `admin` → 200 on `/metrics` and `metrics` → 403 elsewhere, storcon included.
- **RT4-6 (important; §4).** The `:3081` secret is `cloud_admin`-grade. `/grants` narrowed to `USAGE`/`CREATE` on non-superuser-owned schemas for ordinary existing grantees (no superuser, `neon_superuser`, `cloud_admin`, `pg_*` or Chelabase-managed role); `/extensions` installs only trusted extensions. The no-file-read test runs on the image's real extension set (RT4-1).
- **RT4-7 (important; §8).** A `/configure` without `storage_auth_token` on a compute that holds one is refused (400, file kept); `POST /storage_token` refuses an empty or invalid token. "No token = no auth" only for a compute that started without one.
- **RT4-8 (important; §8).** Every `Debug` of a spec redacts `storage_auth_token` (`compute_promote.rs:155` included); the no-token-in-logs test covers the promote path.
- **RT4-9 (minor; §7).** compute_ctl's `Metrics` arm decides by route regardless of `compute_id`: only `/metrics` and `/autoscaling_metrics`.
- **RT4-10 (minor; §4, §5).** The internal middleware has no bypass and never logs the secret; `INSTANCE_ID` set → internal routes still 401.
- **RT4-11 (minor; §8).** `--sync-safekeepers` runs with no `NEON_AUTH_TOKEN` and authenticates from the file; the config and token file are written before the sync on both paths (asserted).
- **RT4-12 (minor; §4.1).** The cache records the open descriptor's identity (`fstat`), re-reads on a same-tick double refresh (new inode), and drops its value on any failed re-read; each case tested.
- **RT4-13 (minor; §3, §9).** The proxy's password file fails closed (empty, missing, URL with a password) and never prints the password (already §9; pinned). `chelabase_keys`: `ROLLBACK PREPARED` of a streamed transaction and the implicit crash abort (`ReorderBufferAbortOld`) write nothing; the per-xid entry is freed on every end.

### 17.3 One pgrx version

Each extension's latest release asks for: pg_graphql 1.6.2 `=0.19.2`; pg_anon 3.2.3 `0.19.1` (caret: any 0.19.x ≥ 0.19.1); pgx_ulid 0.2.3 `^0.17.0`; pg_jsonschema 0.3.4 `0.16.1`; pg_session_jwt 0.5.0 `0.16.1` (its `Cargo.toml` at each tag, read here). No single version satisfies all; **0.19.2** (S20) satisfies pg_graphql and pg_anon unpatched. So:
- One `rust-extensions-build` layer: `cargo install --locked --version 0.19.2 cargo-pgrx` and `cargo pgrx init` for the major; the pgrx 0.11, 0.12 and 0.14 layers (`:1094-1146`) and every `sed` on a `Cargo.toml` are deleted.
- A small patch per extension that asks for another version, pinning `pgrx` and `pgrx-tests` to `=0.19.2`: `pgx_ulid` (0.17 → 0.19), `pg_jsonschema` and `pg_session_jwt` (0.16 → 0.19). pgrx's API changed between 0.16 and 0.19, so these patches may touch source too; each is kept small and its extension's own `cargo pgrx test`/regression must pass. If an upstream release already bumped pgrx by the time the plan runs, that release is taken instead of a patch. No second pgrx layer under any outcome.
- pg_session_jwt's `pgrx-tests` is a path dependency on its own workspace member; the patch updates that member too.

### 17.4 pg_partman's background worker

5.5 makes `pg_partman_bgw.role` required (default `partman_maintainer`) and recommends a non-superuser that owns every partition set it maintains (pg_partman 5.5.0 `doc/pg_partman.md`). Chelabase computes preload only `neon` (`crates/chelabase-neon/src/spec.rs`, `shared_preload_libraries`), so the worker doesn't run today and doesn't start this round. Ruling S21: the role is the branch owner role `postgres` (it owns the tables made through Chelabase, and is not a superuser unless the owner opted in); Chelabase's spec builder adds `setting("pg_partman_bgw.role", "postgres", "string")`, which compute_ctl writes into `postgresql.conf` with the other spec settings (a placeholder until the library is preloaded). Enabling the worker (preloading `pg_partman_bgw`, `pg_partman_bgw.dbname`) is a later step.

### 17.5 Interactions with the security sections

- **RT4-1:** the image test enumerates every trusted extension of `extensions-all`, so every bumped extension (pg_anon 3.x and pg_duckdb 1.1.1 above all) is covered; pg_duckdb 1.1.1 keeps `duckdb.postgres_role` unset, `duckdb.disabled_filesystems` pinned, and S22's auto-install/auto-load pins (DuckDB's `httpfs` could otherwise reach `127.0.0.1:3080/3081` for whoever may run DuckDB).
- **§4.1:** dropping pgrag leaves the shipped `minimal` image with no extension that makes HTTP calls or reads files.
- **pg_session_jwt** (bumped, `extensions-all` only) is Neon's JWT session extension; Chelabase doesn't use it, and its bump doesn't touch Chelabase's auth.
- **pg_cron** (minimal, trusted) runs jobs as their owner; unchanged by the bump.
- No conflict found with D1–D3, U1–U4 or RT4-2..13.

### 17.6 Build cost and how the plan splits it

`extensions-all` from scratch is the round's longest build: V8 (plv8), DuckDB (pg_duckdb), rdkit and the PostGIS stack (plus CGAL if SFCGAL needs it) are each long single-target compiles; dropping pgrag removes the onnxruntime build from both variants. The plan budgets machine time for it (an estimate, to be measured on the first build) and, per the "Build once" rule, builds `extensions-all` once, from the final `round-4`, with the dev images.

Proposed parallel tasks (each in its own fork clone; at most 2 heavy Docker builds or `ci-local.sh` containers at once; each task builds only its own `--target <ext>-build` stages to prove them and runs their `neon-test.sh` in the extension-test harness, the full `extensions-all` build stays the end-of-step one):
1. **pgrx group** (opus coder: API changes): the 0.19.2 layer, pg_graphql, pg_jsonschema, pg_session_jwt, pgx_ulid, pg_anon 3.2.3 (+ `anon_v2.patch`).
2. **PostGIS stack**: SFCGAL 2.3.0 (+ CGAL if needed), PostGIS 3.6.4, pgrouting 4.0.2, h3 + h3-pg 4.5.0.
3. **Heavy C/C++**: rdkit, plv8 (patch rework), pg_duckdb 1.1.1 (RT4-1's patches and pins) and pg_mooncake's removal.
4. **C extensions** (sonnet): the minimal three (timescaledb, pg_partman, pg_cron) and every row 4–5, 18–32 (pgvector's patch rework included).
5. **Binaries and removals** (sonnet): pgbouncer, the three exporters, the build-tools `sql_exporter` bump, and every §17.1 removal (Dockerfile, manifest, `docker-compose/` harness).
Tasks 1–3 are the heavy compiles: run two at a time, task 4 and 5 alongside a single heavy one.
