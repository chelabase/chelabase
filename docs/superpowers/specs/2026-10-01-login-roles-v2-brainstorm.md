# Step 6a re-spec (SQL-managed roles): brainstorm decisions

Running record of the user's answers while brainstorming the 6a re-spec (2026-10-01). Research: `2026-10-01-sql-roles-research.md`. The spec will be written from this.

Goal (user): projects run their existing migrations and they work out of the box; raw SQL on roles applies firmly as long as it doesn't violate the system. Understanding note confirmed by the user (no corrections).

## Answers
1. **Restores and branches from the past: split by origin.** Roles made in SQL follow the database's history (a restore to T keeps only the SQL roles that existed at T, with their passwords at T). Roles made in Studio/the API keep their current existence and password.
2. **Password strength: off in self-hosted mode (opt-in switch to enforce), on in platform mode** (weak passwords refused with an error naming the rule).
3. **Pre-hashed passwords: SCRAM hashes accepted in self-hosted mode only; platform mode refuses every pre-hashed password (like Neon). MD5 refused in both modes** with an error saying to set a plain password.
4. **Passwords typed in SQL are not revealable:** only the SCRAM hash is kept; the plaintext is dropped at once. Studio marks the role "password set in SQL"; its reveal has no password; "Reset password" makes a new revealable one.
5. **One shared set of login roles:** SQL can ALTER/RENAME/DROP/GRANT any login role, Studio-made ones included (the owner gets ADMIN on them); Studio/API list, reset and delete SQL-made ones. Guards apply to both sides. A role's origin (Studio or SQL) stays fixed for the restore rule (answer 1).
6. **Child branches keep the parent's passwords** for every copied role, SQL-made and Studio-made (like Neon; test pipelines just work); after the fork each branch's passwords are independent. **6a also adds a per-branch "protected" flag** (API and Studio toggle): children of a protected branch get fresh passwords for every copied role (like Neon). 6a's fresh-password-per-child rule is dropped. Sources: neon.com/docs/manage/branches, neon.com/docs/guides/protected-branches.
7. **The cap counts login roles only** (SQL- and Studio-made); group roles without LOGIN are unlimited. **Default 50**, configurable, allowed 0..=500; the proxy's role cache sized to match. A CREATE ROLE past the cap fails its transaction with an error naming the setting.
8. **Control plane unreachable: the transaction fails** (Neon's behaviour) with a "role changes are unavailable, try again" error; nothing changes. Only role/database DDL is affected.
9. **Privileges given in SQL stick;** the worker never undoes them for SQL-made roles. **The data API re-checks a secret key's role** (cached ~30 s): if it has become owner-level, requests with that key are refused with an error naming the role until it's plain again or the key uses another role; Studio shows the key as blocked.
10. **Databases created in SQL are tracked and shown:** forwarded database changes (create, rename, owner, drop) are recorded per branch; Studio lists them and the connection panel gets a database picker. Not added to the compute spec; restores follow history.
11. **The protected flag:** children get fresh passwords for every copied role, and the branch refuses delete and reset-to-parent (409 `branch_protected`) until unprotected. Restore stays allowed. IP allow-lists are a later step.

## Design parts (approved one at a time)
1. **Where roles live — approved.** The database (`pg_authid`, travels with history) is the source of truth for every login role except the owner; `neon_roles` is the proxy's copy plus bookkeeping (`origin` sql|api fixed at creation, `password_enc` only for generated passwords, `login`, observed `level`). The compute spec lists only the owner, so `compute_ctl` never re-creates, re-passwords or re-LOGINs user roles (no fork task needed). Studio-made roles are created by the worker in SQL as `postgres` (owner gets ADMIN), owner-level ones also granted `neon_superuser`; the worker re-applies Studio-made roles after a restore. Postgres databases get `branch_databases` (name, owner, origin). Dropped from built 6a: spec-driven login roles and the `privileged` field, privilege fixed at create, the demotion check, fresh passwords per child. Kept: routes and RPCs (201/204), name rules, sealed API passwords, delete across every database, the version guard, the Studio Roles panel, the live-test setup.
2. **The forwarding receiver — approved.** `neon.console_url` → `PATCH /internal/v1/computes/{endpoint_id}/ddl` on the orchestrator's internal listener, compute-token auth; worker admin sessions `SET neon.forward_ddl = off`. One metadata transaction under the endpoint row lock; renames, then sets, then deletes; idempotent; 200 accepts, a 4xx with a one-line plain-text message fails the user's transaction. Roles: reserved names refused; owner re-passworded in SQL accepted (proxy copy updated, sealed owner password cleared); SCRAM required, MD5 refused, pre-hashed accepted self-hosted only, strength (≥12 chars, ~60 bits) in platform mode or opt-in; no-password roles get no proxy copy (`PASSWORD NULL` removes it); cap 50 refuses past it naming `CHELADB_BRANCH_ROLE_CAP`; drop refused while a live secret key uses the role, else the copy is removed whatever its origin; rename moves the copy, re-seals an API role's password, data keys follow; SQL-created roles get origin `sql`. Databases: create/rename/owner/drop mirrored into `branch_databases`; per-branch limit (default 20, a setting); main database drop/rename refused. Proxy cache invalidated at once and ~1 s later. Control plane down → the transaction fails.
3. **The resync — approved.** Under the endpoint lock after restore, reset-to-parent, branch create (child), any compute re-creation, and periodically in reconcile (the data API health-check batch; catches phantom forwards). One admin query (forwarding off, hex-encoded names): per non-system role name, can-log-in, hash, owner-level (superuser, CREATEROLE/CREATEDB/BYPASSRLS/REPLICATION, or neon_superuser membership); plus databases and owners. SQL-made: database wins (add missing SCRAM roles as origin sql, remove copies of vanished roles, take the database's hash, refresh login/level). Studio-made: control plane wins for existence and password (re-create as postgres with the stored hash, plus neon_superuser if created owner-level; reset a differing hash); grants and ownership follow the data; login/level refreshed. MD5-hashed roles get no copy (Studio flags them); no-password roles no copy; nothing removed for exceeding the cap; `branch_databases` set to the database's list. Changed roles invalidated in the proxy. Failure fails restore/reset/branch create/re-creation with "syncing login roles: …"; in reconcile it's logged and retried.
4. **Branches, restore, protected flag — approved.** Children copy every role and password (resync fills copies before ready; API roles keep origin `api`, sealed passwords re-sealed for the child; from a past point: that time's SQL roles plus the parent's current API roles). Restore/reset follow Part 3. `branches.protected` (off by default; `PATCH …/branches/{branch_id}` `{"protected": true}`, Studio toggle): children get fresh generated (revealable) passwords for every copied login role; delete and reset-to-parent refused with 409 `branch_protected`; restore allowed; deleting a Cheladb database with a protected branch also refused (409 `branch_protected`). **Owner `postgres`: keeps step 5's rule (every branch gets its own owner password)** — user chose (b) as safer without much friction.
   - (Owner choice confirmed after the coordinator's assessment: (b) protects the most powerful credential by default, and friction is low because every branch has its own host, so pipelines already fetch each branch's connection string.)
5. **Data API safety and system roles — approved.** Key creation still refuses owner-level roles. `rest` checks before switching to a secret key's role whether it is owner-level (superuser, BYPASSRLS, or neon_superuser member at any depth), cached 30 s per branch and role; if so the request is refused with data API error `role_not_allowed`. Studio shows the key as blocked from the resync's observed level. Rename: keys follow; drop: refused while a live key uses it; `REVOKE <role> FROM authenticator` applies (the key fails with the existing permission error). System roles (`cloud_admin`, `neon_superuser`, `authenticator`, `anon`, `authenticated`, `cheladb_admin`) are refused by Postgres (owner lacks ADMIN) and by the receiver; table grants to anon/authenticated unchanged. Owner-level roles made in SQL stick; keys can't use them.
6. **API and Studio — approved.** Roles list: name, origin, observed level, login, password (`generated`|`set_in_sql`|`md5_unusable`), blocked_keys, pending, created_at; owner first. Create body `{ name, owner_level?: false }` (renamed from `privileged`); reset (new generated revealable password) and delete on any login role (not the owner's delete); `?role=` reveal returns no password plus `password: "set_in_sql"` when not revealable. `GET …/branches/{branch_id}/databases` → `[{ name, owner, origin, main }]`; reveal takes `?database=`; no database create/delete via the API in 6a. `PATCH …/branches/{branch_id}` `{ "protected": bool }`; `protected` on branch responses; `ErrorCode` `branch_protected` (409). utoipa + regenerated client. Studio: origin and level badges, "password set in SQL" note, MD5 warning, blocked-keys note; role and database pickers in the connection panel; Protect toggle with confirm, disabled Delete/Reset-to-parent with reason, database delete disabled while a branch is protected; Data API keys show Blocked.
7. **Tests, existing data, rollout — approved.** New migration on top of 6a's (origin/login/level on `neon_roles`, optional sealed password for SQL rows, drop 6a's sealed/privileged constraints, `branch_databases`, `branches.protected`); computes re-created once at rollout for `neon.console_url`; roles made in SQL before the change become able to log in after the first resync (README note). Unit (receiver rules table-driven, resync per origin, protected refusals, rest's check, routes, Studio), live (a real migration script through the proxy; restore before it and re-run; child and protected-child passwords; MD5; key's role drop; control plane down; forwarding off then resync; GRANT neon_superuser blocks a key), `just role-e2e` rewritten around a psql migration file, plus neon-e2e, data-e2e, branch-e2e, rest_live, Playwright. No fork task. README "Roles and migrations"; roadmap 6c and the per-project cap note.
- **User (2026-10-01): the product's documentation site must clearly highlight the branch password rule** (the owner gets its own password per branch; other roles keep the parent's unless the parent is protected, whose children get fresh passwords) so people aren't blindsided.
