## Decisions (user, 2026-10-15)

- **D1** The `chelabase_keys` logical decoding output plugin in the Postgres fork, with the TE-RT contract (TE-RT spec §3.1 on `table-realtime`) plus R6 (fixed output settings while decoding) and R7 (each transaction's xid).
- **D2** The `chelabase_realtime` walsender restriction (TE-RT R1), enforced by the fork; the role itself is created by RT1's worker.
- **D3** Member roles (`cb_m_*`): (a) only `cloud_admin` changes them; (b) their logins come only from the orchestrator, by a source-CIDR rule (empty list = no rule, for Kubernetes) **and** TLS client certificates (`clientcert=verify-full`).

## 2. D1: the `chelabase_keys` output plugin

`contrib/chelabase_keys/chelabase_keys.c`, modelled on `contrib/test_decoding` (its `Makefile` pattern: `REGRESS`, `REGRESS_OPTS = --temp-config …/logical.conf`, `NO_INSTALLCHECK = 1`). `_PG_output_plugin_init` sets `startup_cb`, `begin_cb`, `change_cb`, `truncate_cb`, `commit_cb`, `shutdown_cb` and nothing else: no stream callbacks (decoding happens at commit, large transactions spill to disk), no prepare callbacks (a prepared transaction is decoded at `COMMIT PREPARED`), no `message_cb` (logical messages are skipped). `OUTPUT_PLUGIN_TEXTUAL_OUTPUT`.

**Options** (`startup_cb`; Postgres calls it at slot creation with no options and at `START_REPLICATION` with the client's): `max_keys_per_table` (integer 1–10000, default 1000), `max_tables` (integer 1–1000, default 256), `max_message_bytes` (integer 65536–16777216, default 1048576; RT3-3). Any other name, a value that isn't an integer, or one out of range is an `ERROR` (`22023`) naming the option (S3).

**Output: one message per committed transaction that changed rows**, written in `commit_cb`, so the message's position is `txn->end_lsn` (`logical.c:985`), the WAL position the walsender reports for it and what the client confirms:

```json
{"v":1,"lsn":"0/1A2B3C8","xid":7421,"changes":[
  {"rel":16412,"s":"public","t":"orders","op":"i","k":[["42"],["43"]]},
  {"rel":16412,"s":"public","t":"orders","op":"d","k":[["7"]]},
  {"rel":16500,"s":"public","t":"events","op":"c"}]}
```

- `lsn` = `txn->end_lsn` as `X/Y` (S4); `xid` = the top-level transaction's **full** id (`xid8`, epoch included), computed in `commit_cb` as `FullTransactionIdFromAllowableAt(ReadNextFullTransactionId(), txn->xid)` (`src/include/access/transam.h:381`; `twophase.c:942` does the same), so it compares with `pg_current_xact_id()` and never wraps (R7, RT3-2). The function requires the xid to be within 2^31 of the next xid, which a slot decoding live always is. Key order fixed: `v`, `lsn`, `xid`, then `changes` or `"all":true`.
- `rel` = the changed relation's OID (a partition's own OID: R16's mapping to the root is realtime's); `s`, `t` = its schema and name from the historic catalog. Strings go through `escape_json`.
- Grouping: relations in the order of their first change; within a relation the ops in the fixed order `i`, `u`, `d`, `c`; keys in the order first seen; a key at most once per (relation, op). A key both inserted and deleted in the transaction appears under both.
- **Keys** (`k`): one array per row of the PK columns' text output, in the PK index's column order (`indkey`), produced by each type's output function.
- **Keys only when the replica identity is the PK:** `relreplident` `d` with a primary key, or `i` with the replica index equal to the primary key index. No PK, `f`, `n`, or `i` on another index → that relation is `c`.
- Insert → `i` with the new key. Delete → `d` with the old key. Update with no old key in the record → `u` with the new key. Update with an old key: Postgres logs the old key when a key column changed **or** has an externally stored value (`heapam.c:9589-9590`, passed at `:4228`), so the plugin compares the old and new key texts: equal → `u` with that key; different → `d` old key and `i` new key (RT3-9).
- A new-tuple PK value that is an unchanged TOASTed value (decoding passes an on-disk pointer) is read from the old key, which Postgres logged flattened for exactly that case: `u` with the old key. Only if no old key exists either (it can't, per `heapam.c:9589-9590`) does the relation become `c` (S5, RT3-9).
- `TRUNCATE` → `c` for each truncated relation (`truncate_cb`).
- **Bounds:** once a relation's distinct keys in the transaction (all ops together) exceed `max_keys_per_table`, its keys are dropped and it is `c`; once the transaction touches more than `max_tables` relations, or the keys collected so far would make the message longer than `max_message_bytes` (long text keys), the message is `{"v":1,"lsn":…,"xid":…,"all":true}` and collection stops (RT3-3). Memory per transaction is therefore bounded by the options; the per-transaction context is reset in `commit_cb`.
- **Nothing for** a transaction without row changes (no message at all; the client confirms from keepalives), catalog changes (decoding never hands catalog relations to `change_cb` unless they are `user_catalog_table`), and logical messages.
- **R6, fixed output settings:** `begin_cb` takes a GUC nest level and sets, with `GUC_ACTION_SAVE`, `DateStyle = 'ISO, YMD'`, `TimeZone = 'UTC'`, `IntervalStyle = 'iso_8601'`, `extra_float_digits = 3`, `bytea_output = 'hex'`, `lc_monetary = 'C'` (a `money` key) and `search_path = ''` (output functions that print qualified names, e.g. `regclass`, print them in full); `commit_cb` restores them (`AtEOXact_GUC`); an error in between is unwound by the decoding transaction's abort. Once per transaction rather than per change (RT3-8): postgres_fdw's `set_transmission_modes` / `reset_transmission_modes` pattern (`contrib/postgres_fdw/postgres_fdw.c:3910-3950`). Whatever the session, the database or the role sets, keys come out in this one form, and nothing leaks into a SQL-interface session.

**Regression tests** (`make check` in the contrib directory, through the SQL interface `pg_create_logical_replication_slot(…, 'chelabase_keys', temporary => true)` / `pg_logical_slot_get_changes`, LSN and xid masked by `regexp_replace` and checked separately): `basic` (insert, update, delete; one message per transaction; grouping and order; duplicates once), `pk_kinds` (int, bigint above 2^53, numeric, text with quotes and unicode, uuid, timestamptz under a session `TimeZone` and `DateStyle` that differ from R6's, interval, float8, bytea, enum, `money` under a session `lc_monetary` other than `C`, `regclass` under a session `search_path` that would shorten it, a composite PK in index order differing from column order), `pk_update` (`d` + `i`; an update setting the PK to its own value → `u`), `toast` (a PK value stored out of line, unchanged in an update of another column → `u` with the full key), `truncate`, `limits` (`max_keys_per_table` 2 → `c` at the third key; `max_tables` 2 → `all`; `max_message_bytes` 65536 with long text keys → `all`; each ceiling plus one refused), `replica_identity` (default with and without PK, `FULL`, `NOTHING`, `USING INDEX` on the PK and on another unique index), `partitions` (a change to a partition carries the partition's OID), `options` (unknown name, non-integer, out of range, valid), `empty` (a transaction with only DDL, or a rolled-back one, emits nothing; `ALTER TABLE` mixed with an insert emits only the insert), `xid_lsn` (the message's `xid` equals `pg_current_xact_id()` of the transaction, as `xid8`, and its `lsn` equals `pg_logical_slot_get_changes`' `lsn` column), `prepared` (decoded at `COMMIT PREPARED`). A forced epoch above 0 can't be reached from SQL in `make check`, so it is tested in Python (§3's suite): the cluster is initialised with `pg_resetwal --epoch` (or `-e`) set to 1 before start, and the message's `xid` must equal `pg_current_xact_id()` there too (RT3-2).

**Python (Neon suite, a real Neon compute):** `test_chelabase_keys.py::test_keys_over_replication_and_restart` on `neon_simple_env`: a role `chelabase_realtime` (`LOGIN REPLICATION`), a `replication=database` connection, `CREATE_REPLICATION_SLOT rt_t TEMPORARY LOGICAL chelabase_keys`, `START_REPLICATION`, rows changed through a normal connection arrive as messages; the endpoint restarts; the replication connection ends and `pg_replication_slots` has no `rt_t`.

## 3. D2: the `chelabase_realtime` walsender restriction

**Where: Postgres core** (`walsender.c`, `postinit.c`), not the neon extension. The walsender has no hook in `exec_replication_command` (`walsender.c:2040-2264`) and the SQL fallthrough is decided there (`:2086-2101`, then `postgres.c:4791-4794` runs `exec_simple_query`), so an extension can't refuse replication commands without a new core hook anyway; a check written directly in core can't be skipped by a missing `shared_preload_libraries` entry either.

**How the role is identified: by name, a compile-time constant** `CHELABASE_REALTIME_ROLE "chelabase_realtime"` (with `CHELABASE_KEYS_PLUGIN "chelabase_keys"`) in `src/include/replication/chelabase.h`, compared with the **authenticated session user's** name once, at connection start. A GUC set by compute_ctl was rejected: a compute started without it (an old spec, a mistake) would fail open, and it adds a setting to protect. The name can't be taken over: only a superuser can rename, alter or drop a role it doesn't hold `ADMIN` on (`user.c:1432`, `:1178`), the worker creates it as `cloud_admin` (TE-RT R1), D3a's check also refuses it to non-superusers (§4.1), and the DDL receiver refuses any `chelabase_` name (`services/orchestrator/src/internal/ddl.rs:496-509`, its message at `:630-632`, via `is_reserved_for`). A role created under that name on a branch where it doesn't exist yet is restricted too (fails closed).

**Rules** (all refusals `42501`, message `permission denied for replication command "<tag>"` or, at login, `role "chelabase_realtime" may only open logical replication connections`):
1. **Logins** (`postinit.c`, right after the replication-attribute check, `:972-983`): a session whose authenticated user is the role must be a database walsender (`am_db_walsender`); a normal backend, a physical walsender (`:991-1011`) and a background worker are refused with `FATAL`. So no SQL session exists for it, and no SQL slot function (`pg_create_logical_replication_slot`, `pg_logical_slot_get_changes`, `pg_replication_slot_advance`, `pg_drop_replication_slot`) can ever run as it.
2. **No SQL in the walsender:** for that role, `exec_replication_command` refuses any non-replication command before it returns `false` (`walsender.c:2086-2101`). The extended protocol and fastpath are already refused in every walsender (`postgres.c:4812`, `forbidden_in_wal_sender`).
3. **Allowed commands:** `CREATE_REPLICATION_SLOT`, `START_REPLICATION`, `IDENTIFY_SYSTEM` (S6). Refused: `DROP_REPLICATION_SLOT`, `ALTER_REPLICATION_SLOT`, `READ_REPLICATION_SLOT`, `BASE_BACKUP` (it would ship the whole data directory), `TIMELINE_HISTORY`, `SHOW`, `UPLOAD_MANIFEST`.
4. **`CREATE_REPLICATION_SLOT`** only `TEMPORARY`, `LOGICAL`, plugin exactly `chelabase_keys`, a name starting with `rt_` (S7), `TWO_PHASE` and `FAILOVER` absent or false, `SNAPSHOT` `'nothing'` or `'export'` (an exported snapshot only lets another session read as itself; `'use'` needs a transaction block, which rule 2 makes impossible), and **at most one slot per session** (S8): with RT1's `CONNECTION LIMIT` on the role, the number of slots it can hold is bounded by its connections.
5. **`START_REPLICATION`** only `LOGICAL`, on the slot this session created: the name must be the one recorded by rule 4 in this process, and the slot (looked up under `ReplicationSlotControlLock`) must still be `RS_TEMPORARY`, logical, `chelabase_keys`, and active for `MyProcPid`. A temporary slot keeps its creator's `active_pid` after the command (`slot.c:729-746` clears it only for persistent slots), so no other session can acquire it (`slot.c:636`); the check stops this role from acquiring anyone's persistent slot (a customer's `pgoutput` slot carries row values, and consuming it would advance it). The plugin options are then validated by the plugin (§2).
6. Everything else in the role's sessions is as for any `REPLICATION NOBYPASSRLS` login; the temporary slot goes with the session (and with a compute restart).
7. **`rt_` names are the role's alone** (RT3-15): `ReplicationSlotCreate` (`slot.c:339`), which every creation path reaches (the walsender, `walsender.c:1266`, `:1297`; the SQL functions and slot copies, `slotfuncs.c:46`, `:139`), refuses a name starting with `rt_` to every session but `chelabase_realtime`'s, superusers included, temporary or persistent; slot synchronisation on a standby (`slotsync.c:773`, which copies the primary's names) is exempt. So no one can fill R17's per-compute count with look-alike slots, or block realtime by taking its names.

**Tests:** Python (Neon suite, `VanillaPostgres` with `wal_level = logical`), `test_chelabase_realtime_role.py`, one test per rule: normal login refused; physical replication connection refused; in a `replication=database` session `SELECT 1` refused, `SELECT pg_create_logical_replication_slot(…)` refused; `DROP_REPLICATION_SLOT`, `ALTER_REPLICATION_SLOT`, `READ_REPLICATION_SLOT`, `BASE_BACKUP`, `TIMELINE_HISTORY`, `SHOW` each refused; `CREATE_REPLICATION_SLOT` refused for a non-temporary slot, a physical slot, `test_decoding`, a name without `rt_`, `TWO_PHASE`, `FAILOVER`, `SNAPSHOT 'use'`, and a second slot in the same session; `START_REPLICATION` refused on a customer's persistent `test_decoding` slot, on another session's temporary `chelabase_keys` slot and physical; the allowed path (`IDENTIFY_SYSTEM`, create, start, a message arrives); a control: another `REPLICATION` role is not restricted; rule 7: a superuser's and another replication role's `rt_` slot (SQL function, walsender, temporary and persistent, `pg_copy_logical_replication_slot` to an `rt_` name) each refused, a non-`rt_` name accepted; and the epoch-1 `xid` check of §2. The restart case is §2's Neon-compute test.

**Not in this round (RT1, TE-RT R1):** the worker creates the role with `admin_sql` as `cloud_admin` (`LOGIN REPLICATION NOBYPASSRLS NOINHERIT`, a `CONNECTION LIMIT`, a platform-secret password, no memberships, no proxy secret). This round only makes the fork enforce what any role of that name may do. The Chelabase live test (§9.3) and §2's regression tests therefore name their slots without `rt_` when they don't run as `chelabase_realtime`.

## 4. D3: member roles (`cb_m_*`)

### 4.1 (a) Only a superuser changes member roles

The worker manages them as `cloud_admin` through `admin_sql` (`crates/chelabase-neon/src/backend.rs:212-224`, `:250-254`): `CREATE ROLE … LOGIN NOINHERIT …`, `ALTER ROLE … PASSWORD`, `ALTER ROLE … NOSUPERUSER …`, `RESET ALL`, `IN DATABASE … RESET ALL`, `NOLOGIN`, `GRANT/REVOKE … TO/FROM` it, `REASSIGN/DROP OWNED BY` it and `DROP ROLE` (`services/worker/src/member_roles.rs:316-383`, `:446-448`; `crates/chelabase-types/src/role_name.rs:69-172`). Postgres today lets a member role change its own password (`user.c:785-786`) and its own settings (`user.c:1038-1040`), and lets a `CREATEROLE` role with `ADMIN` on a group grant that group to it; the reconciler only undoes those later.

**Rule** (in `NeonProcessUtility`, before any forwarding bookkeeping): a statement run while the current user isn't a superuser (`superuser()`, S9) is refused (`42501`, `member role "%s" is managed by Chelabase`) when it names a **protected role** (a name starting `cb_m_` in any case, as `is_member_role` reads it, `role_name.rs:27-29`; or exactly `chelabase_realtime`, §3) as:
- the role of `CREATE ROLE`/`USER`/`GROUP`, or any name in its `IN ROLE`, `ROLE` or `ADMIN` lists;
- the target of `ALTER ROLE` / `ALTER USER` (any option), or any name in `ALTER GROUP … ADD/DROP USER`;
- the target of `ALTER ROLE … [IN DATABASE …] SET/RESET` (`ALTER ROLE ALL` already needs a superuser, `user.c:1071-1076`);
- the old or the new name of `ALTER ROLE … RENAME TO`;
- any role of `DROP ROLE`;
- any grantee or granted role of `GRANT`/`REVOKE` role.

Every `RoleSpec` in these statements is resolved to a name before the test, whatever its kind: a name, `CURRENT_USER`, `CURRENT_ROLE`, `SESSION_USER` (`PUBLIC` is no role) (RT3-13). The hook sees nested statements too (a `DO` block, a PL/pgSQL function, any SPI caller), since `ProcessUtility_hook` runs for them.

Object privileges (`GRANT SELECT ON t TO cb_m_…`) and ownership aren't role statements; the hand-over's `DROP OWNED` keeps clearing them (`role_name.rs:37-104`). Compute_ctl's migrations run as `cloud_admin` and pass (`0002-alter_roles.sql` alters every non-privileged role, member roles included).

**Tests:** Python `test_member_role_guard.py` (`VanillaPostgres` with the neon extension, as `test_ddl_protected_database.py` sets it up): every statement form above refused for a `CREATEROLE` role holding `ADMIN` on a group, and for the member role itself (`ALTER ROLE CURRENT_USER PASSWORD`, `ALTER ROLE CURRENT_ROLE PASSWORD`, `ALTER ROLE SESSION_USER SET`, `ALTER ROLE CURRENT_USER SET`); a quoted upper-case `"CB_M_X"`; `ALTER GROUP g ADD USER cb_m_…`; the same statements inside a `DO` block and a PL/pgSQL function (SPI); each allowed for a superuser; ordinary roles unaffected; the refusal leaves no forwarded change (the mock control plane receives nothing).

### 4.2 (b) Logins only from the orchestrator: source addresses and client certificates

**Today:** `pg_hba.conf` comes from the basebackup (`pageserver/src/basebackup.rs:379-385`, `libs/postgres_ffi/samples/pg_hba.conf`: `trust` for local and loopback), and compute_ctl appends `host all all all md5` (`compute_tools/src/params.rs:9`, `spec.rs:157`). Member roles have no proxy secret, so the proxy can't log in as them, but any container on the compute network that learns a member password can.

**Spec (compute_api):** a new optional `ComputeSpec.member_logins: { allowed_cidrs: [string], client_cns: [string] }` (serde default `None`; unknown fields are already ignored), and `TlsConfig` (`responses.rs:312-315`) gains an optional `ca_path`. Both are lists so a second client (RT1's realtime, if it is given its own certificate) is one more CN and one more CIDR, with no fork change (see "Not in this round").

**compute_ctl** (`update_pg_hba`, called from `prepare_pgdata`, `compute.rs:1555-1568`, on a fresh `pgdata` at every start): writes this block **at the top** of `pg_hba.conf`, before the basebackup's `trust` lines (so loopback and the Unix socket don't admit member roles either) and before the `md5` catch-all:

```
# chelabase: member logins (cb_m_*) only from the orchestrator
hostssl all /^cb_m_[0-9a-f]{32}$ <cidr> scram-sha-256 clientcert=verify-full map=chelabase_member   # one line per CIDR
host    all         /^[Cc][Bb]_[Mm]_ all reject
host    replication /^[Cc][Bb]_[Mm]_ all reject
local   all         /^[Cc][Bb]_[Mm]_ reject
local   replication /^[Cc][Bb]_[Mm]_ reject
```

and to `pg_ident.conf` one line per entry of `client_cns`: `chelabase_member  <cn>  /^cb_m_[0-9a-f]{32}$`. Each CN must match `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` before it is written (no whitespace, quotes, `/` or `#` can reach the file); an empty list or a bad CN fails the start (RT3-12).
- An **empty** `allowed_cidrs` writes one `hostssl` line with address `all`: no source rule (Kubernetes: pod addresses change; certificates plus a NetworkPolicy do the job).
- `member_logins` absent, or TLS not configured for the compute (below), writes only the `reject` lines: member logins are refused (fails closed; a `hostssl` line with `ssl = off` would also stop Postgres from loading the file).
- An `allowed_cidrs` entry that isn't an address/prefix fails the start (`Failed`, with the entry in the error).
- The block is written once per start; a CIDR change applies at the next compute restart (reconfigure doesn't rewrite `pg_hba.conf`, `compute.rs:1992-2079`) (S10).
- `ssl_ca_file = '<ca_path>'` is added to `postgresql.conf` next to `ssl_cert_file` (`config.rs:177-189`) whenever TLS is on and `ca_path` is set, with or without `member_logins` (RT3-12); Chelabase always sends it.

**Postgres fork, `hba.c`:** Postgres accepts `map=` only for `ident`, `peer`, `gssapi`, `sspi` and `cert` (`hba.c:2059-2066`), so `scram-sha-256 clientcert=verify-full` can only compare the certificate's CN with the user name itself, and one orchestrator certificate can't carry every member role's name. ## 6. D5: databases born closed on a protected branch

**How the compute knows the branch is protected:** the guard is in the current database. A protected branch carries the guard's two event triggers in every connectable database and in `template1`; an unprotected one carries none (PB S2, `services/worker/src/member_roles.rs:1205-1245`). `neon.protected_databases` (`crates/chelabase-neon/src/spec.rs:213-218`) only protects the main database from `DROP` and says nothing about protection. The C test: event trigger `chelabase_schema_guard_ddl` exists in the current database (`get_event_trigger_oid`, `event_trigger.c:579`), is owned by a superuser and is `ENABLE ALWAYS`. A customer's look-alike is ignored: an event trigger made through the neon extension ends up owned by its creator (`neon_ddl_handler.c:1675-1690`), not a superuser.

**"Template lacks the guard" can't be read in C:** the template's `pg_event_trigger` lives in another database, and `CREATE DATABASE` can't connect to it. A shared marker (a database setting or comment the reconcile writes) would be a second copy of the guard's state that can go stale, and trusting `template1` fails open whenever its guard is missing or old (R17 touches it only when another database changed). So (U1): **every** `CREATE DATABASE` by a non-superuser in a guarded database is born closed, whatever its template, `template1` included.

**Invariant (RT3-5): every connectable database on a protected branch carries the guard.** Born-closed databases aren't connectable until the reconcile guarded them; databases closed by their owner before protection get the guard too, while staying closed (U2); platform-made databases come from the guarded `template1` and are checked by the next reconcile. A session therefore only ever runs in a guarded database on a protected branch, which is what makes "the current database carries the guard" a sound test for `CREATE DATABASE`. `ALTER DATABASE` names another database, so its refusal is decided by the **target** as well (below), read from shared catalogs (`pg_database`, `pg_db_role_setting`), never only from the session's database.

**Neon extension (`NeonProcessUtility`)**, for a non-superuser:
- In a guarded database, `CREATE DATABASE` with an `ALLOW_CONNECTIONS` option (any value) or `IS_TEMPLATE true` is refused (`42501`, hint `chelabase:branch_protected`) (RT3-4);
- otherwise, in a guarded database, the statement runs with `ALLOW_CONNECTIONS false` appended (a copy of the parse tree), and in the same transaction the database gets the marker setting `neon.born_closed = on` (a new `PGC_SUSET` boolean of the extension, written with `AlterSetting` while switched to the superuser as the event-trigger path does, `neon_ddl_handler.c:1471-1496`). A database setting of a `PGC_SUSET` variable can't be changed or reset by its owner (`ALTER DATABASE … RESET ALL` keeps settings the user may not reset);
- `ALTER DATABASE … ALLOW_CONNECTIONS` or `IS_TEMPLATE` (any value) is refused when the **target** carries the `neon.born_closed` marker (any branch, whatever the session's database), or when the session's database carries the guard (D5; this also keeps an owner-closed database closed on a protected branch until unprotect or the Studio/API path, U2) (RT3-4, RT3-5). (`CONNECTION LIMIT` stays the owner's, `dbcommands.c:2457-2489`.)
- `datallowconn` can't be changed by a catalog update: catalogs grant only `SELECT` to `PUBLIC` (`initdb.c:1791-1802`) and non-superusers hold no other right on `pg_database`; a test pins `has_table_privilege('neon_superuser', 'pg_catalog.pg_database', 'UPDATE')` false.
- Superusers and unguarded databases are untouched; the hooks compile on every major (`ALLOW_CONNECTIONS` exists since 9.5).

**Postgres fork, `postinit.c` (`CheckMyDatabase`, `:352-356`):** `datallowconn = false` refuses every connection, superusers included, and startup options are read only after this check (`:1205-1215`), so the reconcile couldn't connect to guard a born-closed database. Change: a **superuser** may connect to a database with `datallowconn = false` unless it is a template (`datistemplate`); `template0` stays closed to everyone. compute_ctl already skips closed databases itself (`compute_tools/src/spec_apply.rs:1007-1013`), and the worker lists only connectable ones (`member_roles.rs:495`, `review.rs:35`, `roles.rs:475`), so nothing else starts connecting to them (S19).

**Chelabase (the member-roles reconcile, `services/worker/src/member_roles.rs`):**
- `member_catalog_sql` (`:456-507`, which lists only connectable non-template databases, `:495`) gains a line kind for **closed** databases: every `pg_database` row with `datallowconn = false`, with `datistemplate` and whether `pg_db_role_setting` holds `neon.born_closed=on` for it (`setrole = 0`).
- On a protected branch, every closed non-template database joins the guard loop (`:1205-1224`): the guard is checked and installed there (the reconcile connects as `cloud_admin` through the new superuser rule) (U2). Then, **only for a marked database** and only when its install succeeded, one script in the system database runs `ALTER DATABASE … ALLOW_CONNECTIONS true; ALTER DATABASE … RESET neon.born_closed;`. An unmarked closed database stays closed: its owner closed it (U2). A failed install leaves it closed and is a failure of the run (retried, then the sweep).
- A closed template (only a superuser can make one now, RT3-4; `template0` is one) can't be connected to; the run reports it as skipped, not as a failure (RT3-4).
- On an unprotected branch (protection removed, or a child copied from a protected parent), a marked database is opened and its marker reset with no guard; unmarked closed ones are left alone.
- A marked database that is already open (a run that stopped between the two statements) only has its marker reset.
- **When it opens (RT3-11):** the DDL receiver asks for a reconcile on every forwarded delta that makes a database (`services/orchestrator/src/internal/ddl.rs:774-781`, PB R12), but the delta is sent at the creating transaction's pre-commit, so the run (after the 1 s debounce, `member_roles.rs:83`, `:1534-1546`) can come before the commit. A run requested that way that finds no born-closed database retries once after another debounce. Otherwise the periodic sweep, which already visits every ready normal branch whether it has members or not (`crates/chelabase-metadata/src/members.rs:1272-1281`, `member_roles.rs:1553-1573`), opens it at the latest one sweep interval later (`CHELABASE_MEMBER_ROLES_SWEEP_SECS`, default 300 s, `services/worker/src/config.rs:56-58`). Typically about two seconds; at worst one sweep interval.

**Tests:** Python `test_born_closed_database.py` (`VanillaPostgres` with the neon extension and a superuser-owned look-alike guard trigger): a non-superuser's `CREATE DATABASE` (from `template0`, from `template1`) is born closed with the marker; `WITH ALLOW_CONNECTIONS true/false` and `IS_TEMPLATE true` refused; `ALTER DATABASE … ALLOW_CONNECTIONS` and `… IS_TEMPLATE` refused on a marked target, including **from an unguarded database** (the look-alike trigger dropped in the session's database, the target still marked) (RT3-5), and on an unmarked closed target from a guarded database (U2); `ALTER DATABASE … RESET neon.born_closed` and `RESET ALL` leave the marker; `pg_database` not updatable; a superuser's create and alter unaffected; with the trigger owned by a non-superuser, or absent, and no marker, nothing changes. The closed-database connection rule is in the same Python suite (RT3-10; `pg_regress` would print the temporary socket path in `\c` errors): a superuser connects to a closed non-template database; to `template0` it can't; a non-superuser into the closed database can't. Chelabase live, `member_roles_live`: `a_database_from_template0_is_born_closed_then_guarded` (on a protected branch the owner runs `CREATE DATABASE … TEMPLATE template0`; it refuses connections, then within the reconcile's time accepts them, carries the current guard, and a locked member's DDL there is refused), `a_closed_database_is_guarded_but_stays_closed` (an owner-closed database on a branch that then becomes protected: guarded, not opened, `ALTER … ALLOW_CONNECTIONS true` refused; unprotecting lets the owner open it) and `born_closed_opens_without_a_guard_when_unprotected`. Docs: `apps/docs/content/docs/using/branches.mdx:76` replaces the "few seconds unguarded" sentence with: a database created from SQL on a protected branch takes connections once the guard is in, usually within a few seconds and at most one sweep interval later; a database closed before protection stays closed while the branch is protected.

## 7. D6: compute_ctl applies its migrations before `running`

**Today** `apply_config` spawns the migrations on a background task and returns (`compute_tools/src/compute.rs:1916-1941`); `start_compute` then sets `Running` (`:981`). Migration `0002-alter_roles.sql` runs `ALTER ROLE … NOBYPASSRLS` on every non-privileged role, and the worker's data API bootstrap runs `ALTER ROLE authenticator …` (`services/worker/src/data_api.rs:394`) as soon as `SELECT 1` answers (`services/worker/src/provision.rs:275-306`): the `tuple concurrently updated` collision (roadmap, "Parked for the next Neon fork round").

**Fork:** `apply_config` runs the migrations inline, on the same connection settings, before it returns (it already runs inside the blocking start path, which uses `Handle::block_on` at `compute.rs:937-940`), so `Running` is set only after they finished. Migrations run once per cluster (`neon_migration.migration_id`), so later starts add only the id check.

**Which failures stop the start (U3, narrowing S20).** Each entry of `handle_migrations`' list (`compute_tools/src/spec.rs:255-309`) gets a kind: **fail-open** when it removes a privilege or an attribute (its failure would leave a role with more rights than intended), **fail-closed** when it only grants (its failure leaves the owner with fewer rights), **skip** for `-- SKIP`. Read from the files:

| Migration | What it does | Kind |
|---|---|---|
| 0001 | `ALTER ROLE neon_superuser BYPASSRLS` | fail-closed |
| 0002 | every member of `neon_superuser` `INHERIT`; every other non-`pg_` role `NOBYPASSRLS` | **fail-open** |
| 0003 | `GRANT pg_create_subscription TO neon_superuser` (v16+) | fail-closed |
| 0004 | `GRANT pg_monitor TO neon_superuser WITH ADMIN OPTION` | fail-closed |
| 0005–0009 | `-- SKIP` (only the id is recorded, `migration.rs:101-107`) | skip |
| 0010 | `GRANT EXECUTE` on `pg_export_snapshot`, `pg_log_standby_snapshot` (v16+) | fail-closed |
| 0011 | `GRANT EXECUTE ON pg_show_replication_origin_status` | fail-closed |
| 0012 | `GRANT pg_signal_backend TO neon_superuser WITH ADMIN OPTION` | fail-closed |

The runner stops at the first failure (`migration.rs:143-153`) and the id counter is one number, so a later migration can't run past a failed one. The start therefore fails (`Failed`, with the migration's id and error) when the failed migration **or any later one it left unapplied** is fail-open; otherwise the failure is logged and counted (`compute_ctl_db_migration_failed_total`), the compute starts with fewer owner rights, and the next start retries from the failed one, as today (S20). With today's list: a failure in 0001 or 0002 fails the start (0001 would leave 0002 unapplied); a failure in 0003–0012 doesn't. A future migration that removes a privilege or attribute is declared fail-open when it is added.

The existing `test_compute_migrations.py::test_compute_migrations_retry` (it injects a failure into each migration `i` with the `compute-migration` failpoint, `migration.rs:40-61`, and expects the endpoint to start with `migration_id = i - 1`) changes: for `i` = 1 and 2 the start fails (the endpoint reports `failed` naming migration `i`) and `migration_id` stays `i - 1`; for `i` ≥ 3 it starts as today; in both cases the next start without the failpoint applies the rest.

**Bounded (RT3-14):** the migration connection sets `lock_timeout = '5s'` and `statement_timeout = '2min'` (the bound `apply_config` already uses in lakebase mode, `compute.rs:1878-1884`), so a migration waiting on a customer's lock can't hold the start forever; a timeout counts as a failure under the rule above (fatal when the failed migration or a later unapplied one is fail-open, logged otherwise).

**Worker:** `wait_until_ready` (`provision.rs:278-306`; also used by `branch_create.rs:482`, `branch_switch.rs:391`, `schema_base.rs:477`) is ready when compute_ctl's `GET /status` (JWT-protected, `compute_tools/src/http/server.rs:101-126`; body `ComputeStatusResponse`, `libs/compute_api/src/responses.rs:143-151`) says `running` **and** `SELECT 1` answers. `failed` ends the wait at once with compute_ctl's `error`; an unreachable compute_ctl keeps polling until the deadline, as an unanswered `SELECT 1` does; the container checks (`backend.rs:422-430`) stay. The token is the one `/configure` uses (`crates/chelabase-neon/src/reconfigure.rs:22-39`): a new `chelabase_neon::reconfigure::status(http, control_addr, signer, endpoint_id)` and a `status` method on the worker's `SpecPusher` port (`services/worker/src/ports.rs:1651-1682`).

**Tests:** Python `test_compute_migrations.py::test_migrations_done_when_running`: right after `endpoint.start()` returns (it waits for `running`), `neon_migration.migration_id` equals the number of migrations with no `wait_for_migrations`; `test_fail_open_migration_failure_fails_the_start` (a failpoint in 0002: the endpoint ends `failed` naming migration 2; restarted without it, it runs) and `test_fail_closed_migration_failure_starts` (a failpoint in 0012: the endpoint runs, `migration_id` is 11); the changed `test_compute_migrations_retry` (above); compute_ctl unit tests that the migration connection's options carry both timeouts and that the fatal decision follows the rule (failed kind and later kinds, a timeout counting as a failure) (a live lock race on a starting compute would be flaky). Worker unit tests (fakes): `SELECT 1` answering while the status is `init` keeps waiting; `running` plus `SELECT 1` is ready; `failed` ends at once with its error; an exited container still ends at once. So the bootstrap's `ALTER ROLE` can't overlap a migration: the collision can't happen by construction; the end-of-step live pass runs `rest_live` and `data-e2e`, where it was seen.

## Red-team rulings (2026-10-15)

An opus red-team pass attacked this spec against the code. Each ruling below **supersedes** the section it names, and that section has been edited to match; where a section and a ruling still disagree, the ruling wins. U-marked rulings were decided by the user; the rest are the red-team's proposed fixes, accepted as mechanical.

### User decisions

- **U1 (§6; replaces the open question).** Every non-superuser `CREATE DATABASE` on a protected branch is born closed, whatever its template, `template1` included.
- **U2 (§6).** A database closed before the branch became protected (`ALLOW_CONNECTIONS false`, no marker): the reconcile connects to any closed non-template database on a protected branch as superuser and installs the guard there, but opens only databases carrying `neon.born_closed`. The owner's close is respected; reopening goes through unprotect (or a later Studio/API action, "Not in this round"). Non-superusers can't change `ALLOW_CONNECTIONS`/`IS_TEMPLATE` of any database while their session is in a guarded one.
- **U3 (§7, narrows S20; amended by the user the same day).** Only fail-open migrations are fatal: 0002 (`NOBYPASSRLS`) and any future migration that removes a privilege or attribute, tagged as such in compute_ctl. Grant migrations (0001, 0003, 0004, 0010–0012) fail closed: their failure is logged, non-fatal, and the compute starts with fewer owner rights. Because the runner stops at the first failure, a failure that leaves a fail-open migration unapplied (0001 before 0002) is fatal too.
- **S12 stays in this round** (REASSIGN OWNED's database-owner forwarding fix).
- **RT1's member-role checks** (red-team "for the user" #1): out of this round, recorded in "Not in this round" with the two options; the fork's `client_cns`/`allowed_cidrs` lists already support either.

### Mechanical rulings

- **RT3-1 (§4.2).** A certificate change rewrites the key and certificate in `pgdata` and runs `pg_reload_conf` directly; the compute's status is never touched (today it goes to `ConfigurationPending`, `compute.rs:2133-2138`). Test: `/status` stays `running` across a change.
- **RT3-2 (§2).** `xid` is the full transaction id (`xid8`), `FullTransactionIdFromAllowableAt(ReadNextFullTransactionId(), xid)` in `commit_cb` (`transam.h:381`). Tests compare with `pg_current_xact_id()`, including a cluster forced to epoch 1.
- **RT3-3 (§2, S3).** New option `max_message_bytes` (default 1 MB): past it the message is `"all":true`. Lower ceilings for the other two options. A limits test for each.
- **RT3-4 (§6).** `IS_TEMPLATE` is refused to non-superusers in a born-closed `CREATE DATABASE` and in `ALTER DATABASE` on a marked database; the reconcile reports a closed template as skipped, not as a failure. Tests.
- **RT3-5 (§6).** The `ALTER DATABASE … ALLOW_CONNECTIONS`/`IS_TEMPLATE` refusal is decided by the **target's** marker (`pg_db_role_setting`, a shared catalog), not only by the session's database; with U2 it also applies, for non-superusers in a guarded database, to unmarked closed databases. Invariant stated: every connectable database on a protected branch carries the guard. Test from an unguarded database.
- **RT3-6 (§1).** The `postgres.mk` install line for `chelabase_keys` is guarded to v17; `ci-local_test.sh` tests the guard.
- **RT3-7 (§4.2, S13, S14).** The worker's daily sweep renews the orchestrator's client certificate into `<keys>/orchestrator-tls/` (versioned directory plus an atomic `current` swap); the orchestrator reloads it within 60 s without a restart (`ArcSwap` of the rustls config; the owner-pool key carries the certificate fingerprint).
