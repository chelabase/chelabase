## Where we are

On `main`:
- **HTTP gateway** (Pingora, `services/gateway`).
- **Studio sign-in** through our own pages and `auth` on Zitadel v4.19.1, with a landing page and create-database.
- **Repo layout** (merged): `apps/studio` only; backends under `services/` (gateway, orchestrator, worker, auth); CLI at `tools/cli`; `chelabase dev bootstrap` / `dev token`.
- **Database lifecycle** on Neon (step 4): one tenant, timeline and compute container per database, reached through Neon's proxy:
  - owner role `postgres` plus the data API roles `anon`, `authenticated` and `authenticator`
  - encrypted, re-revealable credentials
  - reset password in step 3's order, serialized per endpoint
  - delete by tombstone
  - reconcile over endpoints, computes and tenants
- **Neon storage stack** (step 1, done): starts with `just deps-up` and backs every database since step 4.
- **`crates/chelabase-neon`** (step 2, done): the storage-controller client, compute spec, SCRAM, LSNs, compute JWTs and Neon ids. The worker and the orchestrator use it.
- **Internal control-plane listener and Neon's proxy** (step 3, done): the orchestrator's internal listener on `127.0.0.1:8083` (proxy API, compute specs, storage-controller hooks), Neon's proxy on `4432` (Postgres) and `4444` (WebSocket and SQL over HTTP), and Valkey for the proxy's cache and query cancel. Merged into local `main` on 2026-09-29, not pushed.
- **Provisioning on Neon** (step 4, done): merged into local `main` on 2026-09-30, not pushed.

Specs are in `docs/superpowers/specs/` and plans in `docs/superpowers/plans/`.

**Findings from step 3 (Tasks 8-10):**
- **No extra proxy flags were needed.** `@neondatabase/serverless` 1.1.0 works with `wsProxy = <ep>.localtest.me:4444/v2` and `fetchEndpoint = https://<ep>.localtest.me:4444/sql`, the proxy CA through `NODE_EXTRA_CA_CERTS`, and Node 24's built-in `WebSocket`.

## Decisions made

### Which Neon parts to keep and which to re-engineer

| Neon component | Decision | Why |
|---|---|---|
| pageserver, safekeepers, storage broker, storage controller | **Adopt unchanged** | This is the storage engine behind branching and point-in-time restore. Rewriting it would be the whole project. |
| compute image (Postgres 17 + neon extension) and `compute_ctl` | **Adopt unchanged** | Plain Postgres can't read from the pageserver. `compute_ctl` starts Postgres from a JSON spec served by the control plane. |
| **proxy** (Postgres wire) | **Adopt instead of writing our own pgproxy** | It already does SCRAM, routing by SNI (`<endpoint>.<domain>`), caching of wake results, retries while a compute boots, and rate limits. Its dependency on the control plane is only three calls. |
| Control plane | **Build it ourselves** | Neon's is closed source. |
| NeonVM, autoscaler-agent, vm-monitor | **Drop** | They're tied to Kubernetes and KVM. We replace them with our own **Docker-native compute runtime**, where Chelabase can actually be better than Neon. |
| Neon's Data API | **Not available; build our own** | See the data API section below. |

### What Neon's proxy needs from us

`--auth-backend=control-plane` calls our control plane with a Bearer token. It needs these three calls (from `proxy/src/control_plane/client/cplane_proxy_v1.rs`):

| Call | What we return |
|---|---|
| `GET get_endpoint_access_control?endpointish=&role=` | `role_secret` (a SCRAM-SHA-256 verifier), `allowed_ips`, `project_id`, … |
| `GET wake_compute?endpointish=` | `address` (host:port of the compute), `server_name` |
| `GET /endpoints/{id}/jwks` | JWKS; only needed for the proxy's JWT path |

- The proxy's **serverless side is on, in password mode** (`--wss`: WebSocket and SQL-over-HTTP), so Neon's serverless driver (`@neondatabase/serverless`) works against Chelabase. It needs nothing beyond the two calls above. (Changed 2026-09-28 during step 3; the first draft kept it off. We'll be patching Neon anyway, so splitting HTTP between Pingora and the proxy is acceptable.)
- The proxy's **JWT mode** (`--is-auth-broker`) stays off until step 6. At the pinned ref it replaces password auth on HTTP rather than adding to it, and it needs the `/jwks` call, `local_proxy` on the compute and `pg_session_jwt`. It depends on the data API's end-user identity decision.
- The proxy's **REST broker** (`--is-rest-broker`) stays off for good: its engine is closed (see the data API section).
- That gives these front doors:
  - **Postgres wire and Postgres-over-HTTP/WebSocket** go through Neon's proxy (`:4432` and `:4444` locally).
  - **Everything else over HTTP** (Studio, the platform API, the data API) goes through the Pingora gateway.

### Mapping our model to Neon's

- **Our model:** tenant → project → database, where one database is one container.
- **Neon's model:** tenant → timeline (branch) → endpoint (compute) → roles and databases.
- **The mapping:** one Chelabase database becomes one Neon tenant, with a `main` branch, one endpoint and the `postgres` owner role. A branch is a later addition: another timeline under the same database.

### Valkey: where else it helps

Step 3 adds Valkey 9.1.2 (BSD-3-Clause, protocol-compatible with Redis) for Neon's proxy: clearing its role-secret cache, and query cancel. Once it's in the base Compose profile, these places in the current code could use it. None of them are scheduled; each needs its own decision.

| Where | Today | With Valkey |
|---|---|---|
| `auth` rate limits (`services/auth/src/guard.rs`, `RateLimiter`) | A `Mutex<HashMap>` in one process. Limits reset when `auth` restarts, and two replicas would each allow the full limit. | `INCR` + `EXPIRE` counters shared by every replica, surviving restarts. **Needed before platform mode runs more than one ui-auth.** |
| Gateway (`services/gateway`) | No request rate limits or per-tenant quotas at all. | Per-tenant and per-key limits on the API, shared across gateway replicas. The same pattern would later cover the data API (step 6). |
| Password reset, step 4 (`services/orchestrator`, `reset_password`) | `ALTER ROLE` through the worker. | Publishes `/password_updated` after reconfiguring the compute (required once the proxy caches secrets). |
| Scale to zero, step 7 | Not built. | Last-activity timestamps per endpoint, so an idle-compute reaper can stop computes without scanning metadata. |
| Sign-out everywhere / session revocation (`auth`) | The login cookies are sealed and stateless; Zitadel ends sessions itself. | A denylist of revoked login steps or sessions, e.g. to kill pending sign-ins after a password reset. Only worth it if a real need shows up. |

**Where it doesn't help:**
- **NATS** stays the job queue and request/reply bus; Valkey doesn't replace it.
- **The JWKS cache in `chelabase-auth`** is per process with a 10-minute TTL, and should stay that way; sharing it gains nothing.

**Security finding for the fork (2026-10-01, from step 6 Task 6; a platform-mode blocker).** A database owner (a `neon_superuser` member) can become real superuser:
- the owner runs `CREATE EVENT TRIGGER` (Neon allows it, through `switch_to_superuser` and then `alter_event_trigger_owner` back to the owner), with a plain function that does `ALTER ROLE <owner> SUPERUSER` when `current_user <> session_user`;
- the owner then runs `CREATE EXTENSION pgcrypto`, a trusted extension. Its install script runs as the bootstrap superuser while the session user is still the owner, so the owner's trigger fires with a superuser `current_user`.

The cause is `neon_fmgr_hook` in `pgxn/neon/neon_ddl_handler.c`, which skips non-superuser-owned event-trigger functions only when `GetSessionUserId()` is a superuser. Reproduced live on `compute-node-v17:0.1.0` with every `chelabase` event trigger disabled, so it's independent of the data API. The fix: also skip (or refuse) when the current user (`GetUserId()`) is a superuser and the function isn't superuser-owned, with a regression test (owner event trigger + `CREATE EXTENSION` of a trusted extension, and the owner stays non-superuser). The step 6 live test `owner_event_triggers_never_run_as_superuser` (`services/rest/tests/rest_live.rs`) covers only our `GRANT`, and its doc comment points here. The user handed this to the hard-fork session, which recorded it (`neon-fork` `79f091c`); **the user approved it as fork Task 11a (2026-10-01).**

**Encryption in transit (its own step; the user wants it for end users; checked 2026-09-29).**

**Today only the client connection to Neon's proxy is encrypted.** Ports 4432 and 4444 use TLS with a local CA and a `*.localtest.me` certificate. Everything else is unencrypted, and is safe only because it stays on loopback or the Docker network:

| Link | Today |
|---|---|
| Browser → gateway (Studio, platform API, later the data API) | plain HTTP on `localhost:8000` |
| Proxy → compute (Postgres) | plain |
| Compute ↔ pageserver (page service) and safekeepers (WAL) | plain |
| Pageserver and safekeepers → S3 (SeaweedFS) | plain HTTP |
| Proxy, `compute_ctl` and storage controller → internal listener `:8083` | plain HTTP with bearer tokens or JWTs |
| Worker → `compute_ctl` `/configure` (`:3080`) | plain HTTP with JWTs |
| Services → metadata database, NATS, Valkey, Zitadel | plain (Zitadel runs `--tlsMode disabled`) |

**Neon at `NEON_REF` supports TLS on most of its links already, so this likely needs no patches:**
- the pageserver has `listen_https_addr`, `ssl_cert_file`, `ssl_key_file` and `ssl_ca_file`, and `enable_tls_page_service_api`;
- the safekeepers, the storage broker and the storage controller have `listen_https` and SSL cert/key/CA flags;
- the compute has `ComputeCtlConfig.tls` and `PgComputeTlsSettings`, behind the `TlsExperimental` feature;
- the proxy has a client config with root certificates for its connections to computes.

To confirm in the spec: TLS on the safekeepers' WAL service port, and whether `TlsExperimental` is stable enough at our pinned commit.

1. **The edges**, needed for any deploy beyond localhost:

## The data API (`chelabase-rest`)

### Where it stands

Nothing exists anywhere yet:
- **Neon's Data API is closed.** It's a Rust rewrite of PostgREST inside their proxy (`proxy/src/serverless/rest.rs`, feature `rest_broker`). Its query engine, `subzero-core`, is a **stub** in the public repo; the real crate isn't public or on crates.io.
  - Rechecked 2026-09-28: `neondatabase/subzero` (the commented-out git dependency in `proxy/Cargo.toml`) and `subzerocloud/subzero` both 404. The parser, SQL generator, schema introspection and error mapping all come from that crate; rest.rs is only the glue around it.
  - So patching Neon doesn't make its REST broker usable: we'd still write the whole engine, against an unpublished API. We build `chelabase-rest` and use rest.rs as a reference for the glue (the `set_config` order, the config cache, Postgres error → HTTP status).
- **The old repo deferred it.**
- **The scaffold has nothing either.**

### The pattern to copy from Neon

```
client ──HTTPS + JWT──► data API
   1. validate the JWT against the project's JWKS
   2. load the schema and config from a per-database cache; on a miss, introspect the database
   3. parse the request and generate SQL
   4. wake the compute, then connect as `authenticator`
   5. run in one transaction:
        set_config('role', <jwt role | anon role>, true)
        set_config('request.jwt.claims', <claims>, true)
        <generated SQL>
   RLS does the authorization.
```

Settings, read from the database and cached: `db_schemas`, `db_anon_role`, `db_max_rows`, `role_claim_key`. With no anonymous role, unauthenticated requests are refused.

### Agreed direction (2026-09-28)

Our own design, aimed at speed, security and developer experience. It deliberately doesn't mirror PostgREST or Supabase: no URL grammar, no postgrest-js compatibility.

**Service**
- `chelabase-rest`: one multi-tenant Rust service for every database, behind the Pingora gateway.
- It asks our control plane for each compute's address.
- One sqlx `PgPool` per database: capped, closed when idle, dropped when the compute stops (step 7).

**Wire format**
- `POST /v1/query` with a structured JSON query: `{ from, select, where, orderBy, limit }`, plus insert, update, delete and function-call nodes.
- serde parses it into a strict typed syntax tree and rejects unknown fields. There's no string grammar to parse or escape.
- The contract is ours and versioned.

**Engine** (the user's design)
- One generated query per request, wrapped in `coalesce(json_agg(t), '[]')::text`. The bytes go to the client unparsed, with no JSON round trip in Rust.
- Writes use `WITH r AS (INSERT/UPDATE/DELETE … RETURNING *) SELECT json_agg(r)::text FROM r`.
- **Safety:**
  - Values are always bind parameters (`query_scalar_with`), cast to the column's real type from the schema cache (`CAST($1 AS int4)`), which keeps index use.
  - Table and column names are accepted only if they exist in that database's cached schema, then quoted. No user text reaches the SQL any other way.
- **Per-request transaction:**
  - role and claims set with `set_config(…, true)`, local to the transaction;
  - `statement_timeout`;
  - a row cap (`LIMIT` from settings);
  - row-level security does the authorization.
- **Errors:** SQLSTATE maps to HTTP status (42501 to 401/403, 23505 to 409, P0001 to 400).

**Speed: a shape cache**
- Every value is a parameter, so the generated SQL depends only on the query's shape.
- It's cached per database, schema version and shape hash. Repeat queries skip generation, and prepared statements get reused instead of churning sqlx's statement cache.

**Developer experience**
- `chelabase gen types` introspects the database and writes TypeScript types. The SDK (`@chelabase/client`) is fully typed: column names, filter value types and result shapes. It builds the same JSON tree the server parses.
- Batches: several operations in one request, run atomically in one transaction.
- **Relations (second pass):** `select` can take related tables through foreign keys, each generated as a nested `json_agg` subquery, so one round trip returns nested JSON.

**Considered and rejected**
- **GraphQL:** more machinery, and easier to write a slow query.
- **Raw SQL from browsers:** row-level security would be the only guard. The proxy's SQL over HTTP (port 4444) stays for server-side use.
- **A process per database:** it defeats the shared pools and the shape cache.

### App users: Zitadel identity, an app-owned users table (decided 2026-09-28)

This settles the former open decisions 1 (end-user identity) and 2 (how claims reach SQL).

**Identity: one Zitadel organization per Chelabase project**
- Platform users (people using Studio) stay in the Chelabase organization.
- Each project gets its own organization and app registration for its app users, so users of different projects never mix.
- The SDK's `db.auth.signUp()`, `signIn()` and the rest call our auth service. That's `auth` made project-aware, reusing its password rules, response padding, rate limits and email codes.
- The data API verifies each token and checks that its organization and audience match the database's project.
- **Claims reach SQL through `set_config('request.jwt.claims', …, true)`**, local to the request's transaction. That works on any Postgres.
- Bring-your-own identity providers (Auth0, Clerk, …) can come later, through one trust setting per project.

**The users table belongs to the app.** This avoids the locked, read-only auth table that forces a metadata blob or a second profile table.
- We create it in the app's schema (default `public.users`, name configurable). It has a few **managed** columns: `id`, `email`, `email_verified`, `created_at`.
- Developers add their own columns with normal migrations. It's an ordinary table: foreign keys, joins, indexes, row-level security, and the typed SDK sees every column.
- **Column-level privileges:** only our sync role writes the managed columns; app roles can write every other column. "Users edit their own profile" is one row-level-security policy.
- **An event trigger** blocks dropping or renaming a managed column, with a clear error. Computes run with a superuser we control.
- A helper, e.g. `chelabase_auth.user_id()`, reads the current user's id from the claims for row-level-security policies. The names are ours, not copied from anywhere.

**Atomic sign-up with the app's own columns**
- `db.auth.signUp({ email, password, data: { display_name: "Ada" } })`: `data` maps to the app's columns, and the typed SDK knows which ones exist.
- The order:
  1. generate the user id;
  2. insert the row inside a transaction, where the app's constraints validate the sign-up;
  3. create the Zitadel user with that same id;
  4. commit.

  If a constraint fails, nothing is created in Zitadel. If the commit fails after Zitadel succeeded, the Zitadel user is deleted. There are no orphans on either side.
- **Verified live on Zitadel v4.19.1:** `/v2/users/new` accepts a caller-chosen `userId`.

**Keeping managed columns in sync**
- Zitadel Actions v2 (`/v2/actions`, verified present) sends user events to a webhook on the orchestrator's internal listener. That catches changes made in Zitadel's console, verifications and deletions.
- Event types (verified in our instance):
  - `user.human.added`, `user.human.selfregistered`;
  - `user.human.email.changed`, `user.human.email.verified`;
  - `user.removed`, `user.deactivated`, `user.reactivated`, `user.locked`.
- To check in the spec: how Actions v2 signs webhook payloads, and how we verify the signature.
- A periodic reconcile catches missed events.
- **Deleting a user deletes the row**, cascading to the app's data. A per-project option only marks it deleted, for apps that must keep records.
- **Branches (step 5):** sync updates the users table on every branch of the project, since users belong to the project, not to a branch.

### First subset of operations (decided 2026-09-29)

**First subset of operations:**
- reads with `select`, `where`, `orderBy` and `limit`
- single-table insert, update and delete, returning rows
- function calls
- batches
- `db.auth` sign-up, sign-in and sign-out, with the app-owned users table

Relations and upsert come in a second pass.

## Working rules (still apply)

**How each roadmap step runs (decided 2026-09-29):**
- **Order of work:** a spec, then a plan, then execution task by task. Each task goes to a subagent on a model sized to it (Haiku for transcription, Sonnet for moderate work, Opus for design-heavy or live-debugging tasks), and a review subagent checks it.
- **Run in parallel whenever possible (user's standing rule, 2026-10-01):** every plan maps its task dependencies and schedules independent work concurrently (waves or any other shape): implementers, reviews, research and verification runs. Parallel implementers each get their own short-lived branch and worktree from the step's branch (`just wt-add <branch>-tN`), are reviewed there, then merged back (`--no-ff`) and removed; only work that touches disjoint files runs side by side. Every checkout runs its own stack (`just workbench up|test|run|down|status`), so live tests, e2e runs and browser passes of different tasks run side by side; at most 4 stacks run at once and a fifth `up` waits in a FIFO queue.
- **Checkpoints:** a checkpoint means everything is committed, and a fresh session can resume from files alone. Nothing lives only in chat or in git-ignored folders.
- **The plan's Status block** sits at the top of each plan and is updated and committed at every checkpoint. It holds:
  - the current task, and the tasks done with their commit ranges;
  - every ruling made on the user's behalf, with what it costs if wrong;
  - what's left running (no deferred findings: every finding is fixed in its task's fix round).
- **Pauses:** execution stops for the user at these points:
  - after the spec, for approval;
  - after the plan and its pre-flight scan, for approval;
  - after the end-of-step review and its fixes, before merging.
- **Checkpoints:** after every task (once its review and any fix rounds are done) and at each pause, the plan's Status and this roadmap's "Resume here" are updated and committed. Execution then continues into the next task. Suggest "safe to `/clear`; resume with `continue step N`" only when context is heavy (roughly past 40%) or at the end of a step; a fresh session rebuilding its state costs more than a light context (changed 2026-09-29).
- **Resuming:** read "Resume here", then the plan's Status, then confirm with `git status` and `git log`. Continue at the next task, and never redo a task the Status marks done.
- **Reviews (changed 2026-10-08):**
  - Tasks that are docs only, or small mechanical edits, get no review of their own; the end-of-step review checks them.
  - Every other task gets one review, and every finding (minors included) is fixed in that task's single fix round. The coordinator verifies the fix diff; no second review agent unless the fix changed the design.
  - After a second finding in the same area, the fix round states the invariant and tests it exhaustively (model, property or exhaustive test).
- **The end of a step (changed 2026-10-08):**
  - a whole-branch review on the most capable model, and its fixes, **before** anything is integrated or built;
  - then integration, one gate, one image build (publish settings, no push), one live pass;
  - then a pause for the user's go-ahead to merge, push images (`--push-only`) and pin digests.

### Why (the incidents behind the process rules)

- **Coordinator writes the RED tests (user, 2026-10-13):** an implementer that writes both the tests and the code grades its own homework: the tests can quietly fit what was built rather than what was asked. Plans get longer (full test code), which the user accepted.

- **Build once, nothing deferred (2026-10-07, Neon fork round 2):** fork minors known before integration were deferred by the old "fix minors in one batch at the end" rule, so the gate, image build and live pass ran again for them. The publish script also rebuilt images, so tested and shipped bytes could differ; hence `--push-only`.
- **Invariants after a second finding (2026-10-07):** DDL forwarding went through about 8 review/fix rounds, each finding one more statement sequence. One written invariant and a model test over ~600k sequences then found thousands of violations in one run, all from tracking roles by name.
- **One review, one fix round, short reports (2026-10-07):** chains of review agents, follow-up messages and long reports multiplied turns and tokens without finding more.
- **No polling, simple commands (2026-10-04, 2026-10-07):** agents pinned to a worktree hung ~5 h; `sleep`/`pgrep -f` wait loops ran up to 10 h (a `pgrep -f` pattern matches its own shell); one agent sat 90 min on an invisible permission prompt for `cd … && cargo test`.
- **Verify before reporting status (2026-10-07):** a stalled agent was reported as "running" for over an hour.
- **Check what a filter selects (2026-10-07):** `-k lease` matched every `release-pg17` test and ran the full regression suite for an hour.
- **Hard forks (2026-10-07):** an old policy line ("we do not rewrite the core engine") and "upstream" wording led agents to leave a detach gap open as "upstream's FIXME". The fork's FORK.md and this roadmap now say the whole engine is ours.
- **One stack per checkout (2026-10-13, the workbench rework, W2):** with one shared dev stack, every live test, e2e run and browser pass queued through the one-stack queue, and moving the stack's apps between worktrees swapped one stack under whoever was running. Every live check serialized through the coordinator, and agents could not verify their own work. Each checkout now has its own isolated stack (own Compose project, ports, state, computes), agents run their own, and `wt-remove` purges it.
- **Never `EnterWorktree` (2026-10-04):** a session pinned to a worktree can't touch any other, so three agents hung about 5 h.

- **Worktrees (decided 2026-09-29):**
  - The main checkout stays on `main` and only coordinates.
  - Each branch lives in `.worktrees/<branch>` (`just wt-add`), and subagents work there with absolute paths and `git -C`.
  - Each worktree has its own `target/` (sccache is a machine setting), and `.chelabase` is symlinked from the main checkout.
  - Never use the harness's `isolation: "worktree"`.
- **TDD is strict:** implementers show the failing test run (RED) before writing code, and a report without it goes back.
- **The coordinator writes the RED tests (user, 2026-10-13):** each task's tests are written in full in the plan, committed by the coordinator to the task's worktree before the brief, and run RED; implementers make them pass without changing them; reviewers check those files are untouched. Fix rounds start with the coordinator's failing test per finding.
- Feature branches only. Merge only when the user says. Push the branch after every commit or checkpoint (see `CLAUDE.md`).
- Commit as `git commit`, with `Co-Authored-By` and `Claude-Session` trailers (see `CLAUDE.md`).
- Never run `cargo fmt` across the workspace.
- Never overwrite `.chelabase/secrets/secrets.key` or the gateway key pair.
- The skip-email-verification switch and Mailpit's insecure SMTP auth are for local dev only.
