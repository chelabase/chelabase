Every route is declared once, in `chelabase-routes`, with the credential it takes and an **access level**. The gateway and the services read the same table. The table below is generated from it and checked by a test, so it can't drift.

## Access levels

| Level | Meaning |
|---|---|
| Public | No identity. Health, the API document, sign-in and accept-invite (the code is the credential). |
| Data API key | A data API key, checked by the gateway. |
| Signed in | Any verified identity (`/v1/me`). |
| Instance admin | Self-hosted: an active tenant admin. Platform: an active member of the operator tenant (`CHELABASE_OPERATOR_TENANT_ID`). |
| Tenant member | Any active member of the caller's tenant. |
| Tenant admin | An active tenant admin. |
| Project *role* | The caller's effective platform role on the project is at least *role* (Viewer, Developer, Admin). A tenant admin is Admin on every project. |
| Branch | The minimum depends on the target branch: one role for an unprotected branch, another for a protected one. For merges the target is the branch merged into. |
| Act as | At least the given platform role, and the Postgres role asked for (`?role=`, or the console's and SQL editor's role) must be in the caller's effective set. The owner needs Admin. Owner-level, `LOGIN` and reserved roles, and chains through them, are Admin-only. |

How a refusal answers:

| Case | Status | Code |
|---|---|---|
| No grant on the project (its existence isn't revealed) | 404 | `not_found` |
| Grant too low, or the role isn't allowed | 403 | `forbidden`, with `error.required` (the level needed, `owner`, `role:<name>`, or `connect`) |
| A member with no grants anywhere | 403 | `no_access_yet` |
| A sign-up waiting for approval | 403 | `pending_approval` |
| A feature not designed for platform mode | 403 | `not_available_in_platform_mode` |

`GET /v1/me` returns the caller's capabilities: tenant admin, instance admin, and per project the platform role, the Postgres roles they may act as and (`projects[].databases`) the databases a grant override narrows. It answers 200 for a pending sign-up too, with `member.status: "pending"`. Studio only hides what you can't do; the API decides. See [Members and invites](/using/members-and-invites) and [Roles and schema isolation](/using/roles-and-schema-isolation).

## Effective access

A member's effective access on a project combines their own grant with the grants of their teams (see [Teams](/using/members-and-invites#teams)), then narrows it by their per-database overrides:

- **Union of sources.** The platform role is the best level among the own grant and the team grants. Admin from any source is Admin, holding every Postgres role.
- **Per-role levels.** Each Postgres role keeps the highest level among the sources that name it. An *Act as* route needs the platform level the route asks for **and** the role held at that level or above: a role held only at Viewer can't be used on `POST …/sql`.
- **Narrowing afterwards.** A database override is intersected with the union; it never widens.
- **Checked on every write.** Own-grant, override, team and invite writes are checked on the resulting union for each affected member and database.
- **The data API's extras.** `anon` and `authenticated` are held only when a source names them, Admins included.

`GET /v1/me` reports the union per project. `POST …/tables/{schema}/{table}/cell` (*Act as: Viewer*) for a role held below Developer is read through the data API's connection, so it needs the data API on for the Postgres database (409 `data_api_disabled` when off).
