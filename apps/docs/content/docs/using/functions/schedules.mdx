title: Schedules

A function can run on **cron schedules** per branch. At each due time the function's `scheduled(controller, env, ctx)` handler runs once, with `controller.cron` and `controller.scheduledTime`. See [Handlers](/using/functions/handlers#scheduled-cron).

## Manage schedules

Schedules are managed with the [Management API](/reference/management/functions/listFunctionSchedules) (Developer access on an unprotected branch, Admin on a protected one; Viewer may list):

```bash
BASE="$API/v1/databases/$DB/branches/$BRANCH/functions/cleanup/schedules"

curl -X POST "$BASE" -H "Authorization: Bearer $MEMBER_TOKEN" -H 'content-type: application/json' \
  -d '{"cron": "*/15 * * * *", "timezone": "Europe/London"}'
curl "$BASE" -H "Authorization: Bearer $MEMBER_TOKEN"
curl -X PATCH "$BASE/$SCHEDULE_ID" -H "Authorization: Bearer $MEMBER_TOKEN" \
  -H 'content-type: application/json' -d '{"enabled": false}'
curl -X DELETE "$BASE/$SCHEDULE_ID" -H "Authorization: Bearer $MEMBER_TOKEN"
```

- `cron`: five fields (minute, hour, day of month, month, day of week), so the finest grain is a minute.
- `timezone`: an IANA name such as `Europe/London`. Default `UTC`. The cron is read in that zone, including its daylight-saving changes.
- `enabled`: a disabled schedule never runs. A schedule lists its `next_run_at`.
- `last_error`: `null` normally. When the worker switches a schedule off because its cron or time zone no longer parses, or because it has no upcoming time, `last_error` says why (for example `cron: not a 5-field cron (…)`, `timezone: unknown IANA time zone "…"` or `no upcoming time`). It is cleared when the schedule next gets a next time: on a worker pass that advances it, or on a PATCH that succeeds. You can't set it, and turning a schedule off yourself leaves it `null`.
- An invalid cron or time zone answers 422 naming the field.
- Day and month names (`MON-FRI`, `JAN`) work only in their own field; see [Cron strings that changed](#cron-strings-that-changed).
- A function has at most 20 schedules on a branch; adding a 21st answers 409 `conflict`.

From the CLI:

```bash
chelabase functions schedule add NAME --cron '<5 fields>' [--timezone IANA]
chelabase functions schedule rm NAME ID
chelabase functions schedule list NAME
```

`add` prints the schedule's id (`--timezone` defaults to `UTC`). `list` prints one line per schedule: its id, cron, time zone, enabled or disabled, and `next=` its next run time. The CLI can't edit a schedule or turn one off; the **Schedules** section of Studio's function drawer can, and adds and deletes them too.

## How runs happen

- The worker looks for due schedules every 5 seconds. Several worker replicas never run the same tick twice.
- **One database never takes all the run slots.** A worker runs at most 64 scheduled runs at once, and at most 8 of them for one database. Due schedules left out stay due and run, coalesced, at a later look. A database's share is refilled when the worker next looks, not the moment a run ends, so one database starts at most 8 scheduled runs every 5 seconds.
- **Missed ticks coalesce.** If the worker was down for five minutes, it runs the function once when it returns, not five times.
- **A disabled function skips the run**, and the schedule's `next_run_at` still advances, so enabling it later doesn't replay what it missed.
- A run is an internal call: the function's [auth mode](/using/functions/auth-and-limits) doesn't apply. If the function has a [run-as role](/using/functions/environment#acting-as-the-function), the handler's `env.CHELABASE_SERVICE_KEY` acts as that role; if not, the run still happens, without a key.
- A new branch copies its parent's schedules. They fire for the child only while the function is enabled on it. Deleting a branch or database stops its schedules within one loop.
- A handler that is missing or throws records `scheduled handler: <outcome>` as the function's `last_error`. Runs are not retried; the next tick is the next run.
- The 30 s [wall-clock limit](/using/functions/auth-and-limits#limits) applies.

## Cron strings that changed

Moving to croner 5.0.0 changed what a cron means in these cases. A cron that is no longer accepted answers 422 with `field` `cron` when you create or change a schedule, and that includes a PATCH that sends only `enabled` or `timezone` for a schedule whose stored cron is now rejected. A schedule already stored with such a cron is **disabled at its next due time**: it does not run, its `next_run_at` is cleared, it is still listed (shown disabled, with the reason in `last_error`) and the worker logs a warning with its id. Send a valid `cron` in a PATCH to repair it and turn it back on.

| Cron | Before | Now |
|---|---|---|
| `0 0 * * jan` (a month name in day-of-week) | accepted, ran an unintended schedule | rejected |
| `mon * * * *` (a weekday name in minute) | accepted, ran an unintended schedule | rejected |
| `0 0 * * L` (a bare `L` in day-of-week) | accepted, ran an unintended schedule | rejected |

Still accepted, unchanged: `0 0 * * MON-FRI`, `0 0 1 JAN *`, `0 0 * * 5L` and `*/5 9-17 * * MON-FRI`.

### After an upgrade

When the worker starts, before it runs any schedule, it checks every stored schedule, enabled or not, against the current cron parser and time zone list. It logs one warning for each schedule that no longer parses (its id, branch, function name, cron, time zone, whether it is enabled, and the parser's reason) and one summary line that ends with the count (`rejected=0` when none). It also writes the reason to each such schedule's `last_error`, so the management API and Studio show it before the schedule is switched off. Nothing else about the schedule changes: it is still disabled at its next due time, as above.

To fix one, send a valid `cron` (and `timezone`, if that was the problem) in a PATCH. That turns the schedule back on and clears `last_error`.

Daylight-saving behaviour changed too, for a job at a fixed time in the hour before clocks go forward (a `0 0 * * *` job in `Europe/London` on 2026-03-29): it now runs once that day, at its own time, instead of a second time right after the gap. Searches also cross gaps longer than two hours.
