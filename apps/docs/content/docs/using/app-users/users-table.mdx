---
title: The users table
description: The table Chelabase creates for your app's users, which columns are managed, and how sign-up data reaches your own columns.
---

Every app user has one row in the users table (`public.users` unless you chose another name). The table is owned by the database's owner role (`postgres` unless the database was created with another owner), so you manage it with ordinary migrations.

## Columns

| Column | Type | Who owns it |
|---|---|---|
| `id` | `uuid`, primary key | Chelabase. It is the identity user's id. |
| `email` | `text` | Chelabase. |
| `email_verified` | `boolean` | Chelabase. |
| `created_at` | `timestamptz` | Chelabase. |
| `deleted_at` | `timestamptz` | Chelabase. Set only when `on_delete` is `mark`. |
| `banned_at` | `timestamptz` | Chelabase. Set while the user is deactivated, `NULL` otherwise. |

Every other column is yours. Add columns, constraints, indexes and foreign keys with ordinary migrations.

## Rows are Chelabase's

A guard trigger refuses `INSERT`, `DELETE` and `TRUNCATE` on the table, and any change to a managed column, for every role except `chelabase_auth_sync`. The error is `42501`:

```text
rows of public.users are created and deleted by Chelabase app users
column email is managed by Chelabase app users
```

Your own columns can be updated by the owner, and by users on their own row for each column you grant them (see below).

## Its shape is protected

Event triggers refuse:

- dropping or renaming the table, or moving it to another schema;
- dropping, renaming or retyping a managed column;
- dropping, renaming, replacing or disabling the guard triggers.

A superuser can still get around them (with `event_triggers = off`). The users bootstrap runs again when the branch's compute is re-created, reset or restored, and puts back a dropped table and the triggers.

## It starts locked down

On a new table:

- `anon` has no privileges;
- row-level security is on;
- `authenticated` can select its own row (`chelabase_users_select_own`, `USING (id = chelabase.user_id())`). It holds a `DELETE` grant too, but the guard refuses every delete;
- `authenticated` has no `UPDATE`: no user can change any column until you grant it.

To let users edit one of your columns on their own row, grant it per column:

```sql
GRANT UPDATE (nickname) ON users TO authenticated;
```

The `chelabase_users_update_own` policy keeps that grant to the user's own row. Managed columns stay refused by the guard whatever you grant.

Grant `UPDATE` per column, not on the whole table: every time Chelabase sets the users table up again (re-enabling app users, a repair, a new branch, or the branch's compute being re-created, reset or restored), it removes a table-level `UPDATE` held by `authenticated` and keeps its column-level `UPDATE` grants. A table-level `UPDATE` granted to `PUBLIC` or to a role `authenticated` belongs to isn't removed, and opens every column you add to every user: don't grant one.

The policies aren't protected: change or drop them like any policy. Studio's [RLS warning](/using/studio) names the users table while RLS is off.

## Sign-up data is opt-in per column

`signUp`'s `data` reaches a column only when that column is granted `INSERT` straight to `authenticated`:

```sql
GRANT INSERT (display_name) ON users TO authenticated;
```

Only this column-level grant to `authenticated` counts. A table-level `GRANT INSERT ON users …`, a grant to `PUBLIC`, or a grant to a role `authenticated` is a member of doesn't open a column to sign-up data. Any other key is 422 `unknown_column`. That includes managed columns, generated columns and `GENERATED ALWAYS` identity columns. `REVOKE INSERT (display_name) ON users FROM authenticated` takes a column out again.

The values go through your column types and constraints. A failure is 422 `constraint_violation` with Postgres' message (and the constraint's name when it has one), and no identity user is created.

The generated `db.ts` (Studio's **Download types**, `curl` of `/data/v1/types`; they produce the same module) marks the table, and the SDK types `signUp`'s `data` from its insertable columns.

## Changes for existing projects

Projects whose users table was created before this change:

- **Table-level `UPDATE` is removed.** Earlier users tables gave `authenticated` `UPDATE` on the whole table. The next time Chelabase sets the users table up again (see above), that grant is removed. Column-level `UPDATE` grants you made to `authenticated` are kept. A table-level `INSERT` held by `authenticated` or `anon` is removed the same way, and their column-level `INSERT` grants are kept. A kept column grant that the removal cleared comes back without grant option and with the table's owner as its grantor, and grants that `authenticated` passed on to other roles are removed with the table-level grant. If a table-level grant was made by a role that no longer has `USAGE` on the table's schema, the setup fails and names the table and that role: revoke the grant as that role, or give it `USAGE` again. If users edit their own columns through the data API, grant each such column before then: `GRANT UPDATE (nickname) ON users TO authenticated;`.
- **Sign-up data needs a column-level grant.** A sign-up's `data` no longer reaches a column through a table-level, `PUBLIC` or inherited `INSERT` grant, only through `GRANT INSERT (col) ON users TO authenticated`. Through the SDK, a key for any other column is 422 `unknown_column`.

## Defaults and triggers run as `chelabase_auth_sync`

Rows are written by the sync login `chelabase_auth_sync`, so a column default or a `BEFORE INSERT` trigger of yours on the users table runs with its privileges. Grant it what they touch:

```sql
GRANT INSERT ON profiles TO chelabase_auth_sync;
```

or make the trigger function `SECURITY DEFINER`.

## `on_delete`

When a user is deleted:

- `delete` (default) deletes the row; your foreign keys cascade as you defined them;
- `mark` sets `deleted_at` and keeps the row.

The unique email index (on `lower(email)`) skips marked rows, so the address can sign up again.
