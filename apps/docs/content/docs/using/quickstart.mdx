title: Quickstart
description: Sign up, create a database and connect to it.
---

This takes you from a running stack to a database you can connect to. It uses self-hosted mode, the dev mode, and needs Docker (the worker starts each database's compute container).

## 1. Start the stack and sign in

1. Run `just dev`, then open [http://studio.chelabase.localhost:8000](http://studio.chelabase.localhost:8000) and choose **Sign in** as the bootstrap admin: `just zitadel-bootstrap` makes `zitadel-admin@zitadel.localhost` (or the email you pass to it, `just zitadel-bootstrap you@example.com`) the tenant admin.
2. You land in Studio. Set the bootstrap admin before you expose Studio to anyone: until a tenant has its first member, the first person to sign in claims the admin, so run `just zitadel-bootstrap you@example.com` (positional) first; that fresh-install window exists until the first bootstrap. `.chelabase/zitadel/demo-sa.json` is a tenant-admin credential on self-hosted dev: keep it private. Emails such as invites and password resets land in Mailpit at [http://mail.chelabase.localhost:8000](http://mail.chelabase.localhost:8000).
3. On `/app` you see your project, its databases, and a form to create one.

<Callout type="info">
Self-sign-up is off by default: an admin invites everyone else (an email, or a link to hand over when Zitadel has no email provider), and they join the same organization and tenant, a shared team workspace. An admin can switch open sign-up on; people who then sign up wait for approval. Use `http://studio.chelabase.localhost:8000`: the sign-in redirect and the gateway's CORS settings are registered for that host.
</Callout>

When sign-up is open, the sign-up's email verification follows `CHELABASE_REQUIRE_EMAIL_VERIFICATION` (`true` requires a code, which lands in Mailpit; `false` turns it off); without it the default follows the mode: off when self-hosted, required in platform mode. Invitees verify their email by accepting the invite.

## 2. Create a database

Enter a name in the form on `/app` and create it. The database shows as provisioning while its Neon tenant, timeline and compute are made, then as ready. Studio polls every 2 seconds until the status settles.

From a terminal, `just create-db-demo demo1` creates one through the gateway (give the name positionally: `name=demo1` would become the literal name). `GET http://api.chelabase.localhost:8000/v1/databases/<id>` reports its `status`.

## 3. Connect

Open **Connection details** on the database in Studio, or call `GET /v1/databases/{id}/connection`. You get the owner credentials and a URI such as:

```txt
postgresql://postgres:…@<endpoint>.localtest.me:4432/<db>?sslmode=verify-full
```

Connect with the proxy's CA certificate:

```sh
psql "<uri>&sslrootcert=.chelabase/neon/proxy-ca.crt"
```

If `localtest.me` resolves to `::1` first, also add `&hostaddr=127.0.0.1`. The response's `ca_file` field names the CA file (self-hosted mode; `null` in platform mode). You can show the connection details as often as you like.

## 4. Remove it

Delete the database in Studio (it asks you to type the name) or with `DELETE /v1/databases/{id}`. `just sweep-dbs` removes every database in the dev stack.
