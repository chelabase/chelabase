---
title: "App users"
description: "How app users are stored, authenticated and kept in sync between Zitadel and your database."
---

Apps sign their own end users up and in through `db.auth`, and the data API runs their requests as `authenticated` with the user's claims. For how to enable and use app users, see the [app users guide](/docs/using/app-users). This page covers the moving parts.

## Who holds what

- **Zitadel holds the identities**, one organization per project. It checks passwords and is the source of truth for who exists.
- **Chelabase issues the tokens.** The `auth` service checks the password through a Zitadel session, then signs a short-lived EdDSA access token (`iss` is `chelabase-auth`, `aud` is `chelabase-project:<project id>`) and a rotating refresh token bound to that Zitadel session. The flows live under `/auth/v1/app/` and take a public key.
- **Your database holds a users table** that you own, in one chosen auth database of the project: one row per user, on every branch of that database.
- **The orchestrator keeps the sessions.** Sessions live in the metadata database, which stores only the SHA-256 of each refresh token. The orchestrator rotates refresh tokens, detects reuse and revokes sessions.

## Request path

An app request carries `Authorization: Bearer <public key>` plus `Chelabase-User: <access token>`. The gateway verifies the token with the app-user public key and checks that its session is still live (cached 30 seconds, so a revocation lands within 30 seconds). It then mints the identity token for `rest` with the user's claims, and `rest` runs the request as `authenticated` with `request.jwt.claims` set. Policies read the claims through the `chelabase.claims()`, `chelabase.user_id()` and `chelabase.user_email()` helpers. See [Gateway](/docs/architecture/gateway) for the full check.

The token key pair is made once by `chelabase dev bootstrap` (`.chelabase/auth/app-jwt.key` and `app-jwt.pub`, never overwritten): `auth` signs, the gateway verifies. A public JWKS endpoint (`GET /auth/v1/app/jwks`) lets your own servers verify tokens too.

## Sync, webhooks and reconcile

Zitadel is the source of truth. Three paths copy users into the table on every live branch of the auth database:

- **Write-through** from Chelabase's own flows (sign-up, the platform admin).
- **Webhooks.** `chelabase dev bootstrap` creates one instance-wide Zitadel Actions v2 target that points at the orchestrator's internal listener (`POST /internal/zitadel/events`), with an execution on user events, and writes its signing key to `.chelabase/zitadel/actions.env` (sourced by `just`). The orchestrator checks the signature (401 for a bad one, 503 when no key is configured) and ignores events from other organizations. A user event publishes a sync job; a password change also revokes the user's sessions made before it. Compose relaxes Zitadel's `ZITADEL_HTTPCLIENT_DENYLIST` so Zitadel may call the host (self-hosted dev only).
- **Reconcile.** Every `CHELABASE_APP_USERS_RECONCILE_SECS` (default 300) per enabled project, and right after a branch of the auth database is created, the worker compares the organization's users with each branch's rows and syncs every difference. The same pass reruns enables, disables and project deletes that have been stuck for 5 minutes, and purges sessions that were revoked or expired more than 7 days ago.

The sync writes rows as the `chelabase_auth_sync` role. A guard trigger refuses inserts, deletes and changes to managed columns from any other role, so rows are Chelabase's to create and delete.

## Settings

| Variable | Default | Read by |
| --- | --- | --- |
| `CHELABASE_ZITADEL_ADMIN_PAT_FILE` | from `demo.env` (`.chelabase/zitadel/admin.pat`) | orchestrator, worker, auth (organization and user admin; without it app-user routes answer 503 and jobs wait) |
| `CHELABASE_APP_JWT_PRIVATE_KEY` / `CHELABASE_APP_JWT_PUBLIC_KEY` | from `demo.env` | auth signs, the gateway verifies |
| `CHELABASE_APP_AUTH_INTERNAL_TOKEN` | `chelabase-dev-app-auth` | auth to the orchestrator's internal app routes |
| `CHELABASE_APP_SESSIONS_INTERNAL_TOKEN` | `chelabase-dev-app-sessions` | gateway to session liveness |
| `CHELABASE_ZITADEL_ACTIONS_SIGNING_KEY` | from `.chelabase/zitadel/actions.env` | orchestrator (webhook signatures) |
| `CHELABASE_APP_ACCESS_TTL_SECS` | `900` (60 to 86400) | auth |
| `CHELABASE_APP_REFRESH_TTL_SECS` | `2592000` (30 days; at most 90 days) | orchestrator |
| `CHELABASE_APP_USERS_RECONCILE_SECS` | `300` (30 to 86400) | worker |
| `CHELABASE_INTERNAL_URL` | `http://127.0.0.1:8083` | auth (the orchestrator's internal listener) |

The default internal tokens are for local development only.

## Tests

`just app-users-e2e` (needs `just dev`) runs the whole story live: enabling app users, sign-up and sign-in, row-level security on the users table, branches receiving the rows, a webhook sync, refresh rotation and reuse detection, and project deletion. `app_users_live` (`cargo test -p worker --test app_users_live -- --ignored --test-threads=1`, with the environment named in the file's header) covers the bootstrap, the guard and the worker's enable, sync, resync and disable against a real compute and Zitadel.
