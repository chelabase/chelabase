The gateway is a Pingora proxy on `127.0.0.1:8000` by default (`CHELABASE_GATEWAY_LISTEN` takes a list, e.g. `127.0.0.1:8000,[::1]:8000`). It routes by host name: the API host serves the APIs, and the Studio, docs, landing and mail hosts are passed through to their apps. The auth host serves nothing (every path is 404): it only names the issuer of member tokens. All API traffic goes through it: the Management API (`/v1/*`), the login API (`/auth/v1/*`) and the data API (`/data/v1/*`). It never reads request bodies.

## One declaration per endpoint

Every public endpoint is declared once, in the `chelabase-routes` crate: method, path, owning service, who may call it and which origins may use it from a browser. The gateway routes and applies policy from that list; the owning service builds its axum routes from the same list, so the two cannot drift. The OpenAPI tests also check each document against it (see [API generation](/architecture/api-generation)).

Each request goes through a fixed pipeline: request id, host scope, route, CORS, authentication, internal identity. Nothing is configurable per route except the declared policy.

| Policy | Meaning |
| --- | --- |
| Public | No credential (for example `GET /health`, the sign-in routes, the API reference) |
| Management | A member access token (JWT) |
| Data key | A data API key of either kind (`chk_pub_` or `chk_sec_`) |
| Secret data key | Only a secret key (`GET /data/v1/schema`) |
| Public data key | Only a public key (the app-user sign-in flows); a secret key is refused |

## Management API requests

Management endpoints require `Authorization: Bearer <member access token>`, the EdDSA JWT that `auth` signs at `POST /auth/v1/token` (see [Identity service](/architecture/identity#member-sign-in-and-tokens)). The gateway verifies it locally with the member public key (`CHELABASE_MEMBER_JWT_PUBLIC_KEY`): the algorithm, key id, issuer (derived from `CHELABASE_AUTH_HOST` and `CHELABASE_PUBLIC_SCHEME`; see [Hosts](/self-hosting/hosts)), audience `chelabase-member`, claim set and lifetime are all pinned. Without a verify key every bearer is a 401 and the gateway reports itself not ready. It then forwards the request with an **internal identity token** in the `x-chelabase-identity` header:

- an EdDSA JWT, valid for 60 seconds, signed for exactly one target service (its `aud` is `orchestrator`, `auth`, `rest` or `realtime`);
- the gateway never forwards `Authorization`, the `Chelabase-User` header or a client-supplied `x-chelabase-identity`.

The internal token carries the member's tenant (the member token's `tid`). The orchestrator trusts only that token (it holds the verify key, `CHELABASE_INTERNAL_VERIFY_KEY`) and still requires an active membership in that tenant on every request. Calling the orchestrator's port `:8081` directly returns `401`.

`init-secrets` (or `just workbench up` on a workbench stack) creates the gateway's key pair once; it is never overwritten.

## Data API requests

A data API request carries `Authorization: Bearer <key>`. The gateway:

1. hashes the key (SHA-256) and looks the hash up in a cache (30 seconds; unknown keys are cached for 30 seconds too);
2. on a miss, asks the orchestrator's internal listener for the key's branch, role, project and database allow-list;
3. if the request carries `Chelabase-User: <access token>` (an app user), verifies that token with the app-user public key and checks that its session is still live (cached 30 seconds). A user token is refused with a secret key (400 `user_token_with_secret_key`), and the request then runs as `authenticated` with the user's claims; an invalid, expired or revoked token is a 401, never a fall back to the key's own role;
4. mints an identity token for `rest` that carries the branch, key id, role, claims, project and database allow-list.

`rest` enforces the allow-list, because the gateway never reads bodies. A revoked key stops working within 30 seconds, the cache lifetime.

Cache misses are rate limited to 20 per second per client address, and a request over the limit gets 429 `rate_limited`. The limiter keys on the connection's address, or on the client address forwarded by a proxy listed in `CHELABASE_GATEWAY_TRUSTED_PROXIES`; it ignores `X-Forwarded-For` from anyone else, and groups IPv6 clients by their `/64` prefix. It remembers at most 100,000 addresses (idle ones are forgotten after 60 seconds); past that it evicts entries, and an evicted address starts again with a full allowance. Behind a load balancer every client shares one address.

## Request limits

Data API and storage requests made with a public key are limited at the gateway, after the key and any user token are checked. Each request draws on one token bucket:

- with a verified `Chelabase-User` token, the bucket of that app user on that key, wherever the user is;
- without one, the bucket of that key and the client's address (the same address as above: the connection's, or one forwarded by a trusted proxy, IPv6 grouped by `/64`).

A bucket holds a burst of requests (default 300) and refills at a steady rate (default 100 a second). Past that, a request gets 429 `rate_limited` with `Retry-After` (whole seconds) and the route's CORS headers; `Retry-After` is exposed to browsers. The 429 itself takes nothing, and neither does a request the gateway refuses (a missing, unknown or wrong kind of key, a bad user token, the cache-miss limit), so a request is never limited twice for one cause. The data API and storage have a budget each, so a page loading many files doesn't hold back its queries; `CHELABASE_GATEWAY_STORAGE_RATE_SHARED=true` makes storage draw on the data API's budget.

- **No bucket for a key as a whole.** The public key ships in every browser, so a shared bucket would let anyone who reads an app's page use up the whole app's allowance. The ceiling is per client: a caller spread over many addresses or many app-user accounts is limited per address or account, not in total.
- **Secret keys are not limited.** They belong on servers, where one key carries every user's requests from one address; a leaked secret key is answered by revoking it.
- **One address, many anonymous callers.** Requests without a user token from one address share its bucket: a reverse proxy not listed in `CHELABASE_GATEWAY_TRUSTED_PROXIES`, an app server calling with the public key for its visitors, and functions calling the data API through `env.CHELABASE` without a user token. Send the user's token, list the proxy, use the secret key on the server, or raise the limit.
- **Functions calling for their caller.** A call through a function's [caller-bound binding](/using/functions/environment#the-caller-bound-binding) (`ctx.props.CHELABASE`) carries its original caller's address in `chelabase-original-client-ip`, and draws on that address's bucket instead of the runtime's. The gateway believes the header only when the TCP peer itself is the functions runtime (`CHELABASE_GATEWAY_FUNCTIONS_RUNTIME`; never an address read from a forwarding header), only as one IP literal, and removes it from every request it proxies. It changes nothing else: `X-Forwarded-For`, the cache-miss limit and auth's per-IP limits still see the runtime. On a call to another function the gateway hands the original address on to the functions service.
- Functions (`/functions/v1/…`, `/services/v1/…`), the app-user auth routes (auth has its own limits) and keyless storage downloads (public and signed URLs) are not limited here.
- Limits are kept per gateway instance, in memory: with several gateways a client's allowance is one per instance. Each budget remembers at most 100,000 clients; when it is full, those with the most allowance left go first, and a new client is always tracked.

## Refused MCP bearers

The gateway passes the `/mcp` bearer to `mcp` unchecked, so it counts what `mcp` refuses instead. Every 401 a request to the MCP server gets, the gateway's own for a missing bearer and the one `mcp` answers for a bad, expired or revoked token, counts against the client's address (the same address as above: the connection's, or one forwarded by a trusted proxy, IPv6 grouped by `/64`). An address may have 30 refusals at once and earns one back every 2 seconds. Past that, every `/mcp` request from it gets 429 `rate_limited` with `Retry-After`, before its bearer is looked at, so a good token from that address waits too. The limit is checked when a request arrives, so an address can have as many refusals answered as it has requests in flight before it applies; those refusals still count, which stretches the wait to about a minute at most. A request whose client hangs up before `mcp` answers counts as a refusal too, while a failure of `mcp` itself (502 or 504) never does. Successful requests never count, and the discovery documents (`/.well-known/oauth-protected-resource…`) are never limited.

Only addresses with a refusal not yet earned back are remembered, at most 100,000. When a new address needs room, those that have earned everything back go first, then those with the most allowance left until the table is at seven eighths of its size; a new address is always tracked, so a full table never stops limiting new clients, and a flood from many addresses can't free one that is limited. Behind a load balancer that isn't a trusted proxy, every client shares one address and one allowance.

The gateway answers its own 404 and 405 under `/data/` with the data API's error body (code `invalid_query`), so a client sees one error shape for the whole prefix.

## Forwarding and CORS

- The gateway sets `X-Forwarded-For` to the client's address (never trust it for authorization), `X-Forwarded-Host` to the request's host, and `X-Forwarded-Proto` to `CHELABASE_PUBLIC_SCHEME`. It speaks plain HTTP itself.
- Studio endpoints allow Studio's origin (from `CHELABASE_STUDIO_HOST`); the sign-in routes also allow cookies for it. The data API endpoints allow any origin (`Access-Control-Allow-Origin: *`, never with credentials), so browsers can call them with a public key.
- Only `GET /v1/realtime/socket` takes a protocol upgrade, and only `Upgrade: websocket`; its socket may sit idle up to an hour both ways. Any other API request that asks for an upgrade gets 400 `invalid_request` before it reaches an upstream.
- A host the gateway does not serve gets a 404 with an empty body, and a request without a `Host` a 400 with an empty body: nothing in the answer names the gateway or its hosts.

## Health

`GET /health` is public and answered by the orchestrator. `GET /_gateway/health` is the gateway's own liveness check, answered before any host or route check.

## Settings

| Variable | Default | Meaning |
| --- | --- | --- |
| `CHELABASE_GATEWAY_LISTEN` | `127.0.0.1:8000` | Comma-separated listen addresses |
| `CHELABASE_ORCHESTRATOR_URL` | `http://127.0.0.1:8081` | Management API upstream |
| `CHELABASE_AUTH_URL` | `http://127.0.0.1:8084` | Login API upstream |
| `CHELABASE_REST_URL` | `http://127.0.0.1:8085` | Data API upstream |
| `CHELABASE_REALTIME_URL` | `http://127.0.0.1:8087` | Realtime upstream (tickets and the websocket) |
| `CHELABASE_API_HOST`, `CHELABASE_STUDIO_HOST`, `CHELABASE_AUTH_HOST` | none (required) | The hosts that serve the API and Studio, and the one that names the member tokens' issuer |
| `CHELABASE_DOCS_HOST`, `CHELABASE_LANDING_HOST`, `CHELABASE_MAIL_HOST` | unset | Optional hosts for the docs site, the landing page and Mailpit |
| `CHELABASE_PUBLIC_SCHEME` | `https` | The scheme clients use; derives Studio's origin and the issuer |
| `CHELABASE_GATEWAY_TRUSTED_PROXIES` | none | Reverse proxies whose forwarded client address is believed: CIDRs or addresses, comma-separated |
| `CHELABASE_GATEWAY_UPSTREAM_TIMEOUT_SECS` | `60` | Upstream read timeout |
| `CHELABASE_GATEWAY_DATA_RATE_PER_SECOND`, `CHELABASE_GATEWAY_DATA_RATE_BURST` | `100`, `300` | Data API [request limits](#request-limits): the refill rate (requests a second) and the burst, per key and client |
| `CHELABASE_GATEWAY_STORAGE_RATE_PER_SECOND`, `CHELABASE_GATEWAY_STORAGE_RATE_BURST` | `100`, `300` | Storage request limits, the same way |
| `CHELABASE_GATEWAY_STORAGE_RATE_SHARED` | `false` | `true`: storage requests draw on the data API's budget (the storage settings must then be unset) |
| `CHELABASE_GATEWAY_FUNCTIONS_RUNTIME` | none (compose: `functions-runtime`) | The functions runtime's peers, whose original-caller address is believed ([request limits](#request-limits)): comma-separated host names (resolved every few seconds), CIDRs or addresses |
| `CHELABASE_INTERNAL_URL` | `http://127.0.0.1:8083` | The orchestrator's internal listener, for key lookups |
| `CHELABASE_DATA_KEYS_TOKEN` | `chelabase-dev-data-keys` | Bearer for key lookups |
| `CHELABASE_APP_SESSIONS_INTERNAL_TOKEN` | `chelabase-dev-app-sessions` | Bearer for app-user session liveness |
| `CHELABASE_MEMBER_JWT_PUBLIC_KEY` | unset | Member token verify key (a PEM file, `auth/member-jwt.pub`); unset, every bearer is refused |
| `CHELABASE_APP_JWT_PUBLIC_KEY` | unset | App-user token verify key (a PEM file); unset, every `Chelabase-User` header is refused |
| `CHELABASE_INTERNAL_SIGNING_KEY` | none (required) | The key that signs identity tokens (`gateway/internal-signing.pem`) |

A request limit setting that isn't a positive whole number (or `true`/`false` for the switch) stops the gateway at start-up, naming the variable; blank is the default.

The development bearer values (`chelabase-dev-…`) are used only with `CHELABASE_DEV_DEFAULTS=1` (the workbench); otherwise an unset or development bearer stops the service at start-up. Each bearer can also be given as a file through `<NAME>_FILE`.
