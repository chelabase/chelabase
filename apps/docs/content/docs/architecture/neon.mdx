Chelabase runs Neon's storage stack and Neon's compute, from its own hard fork ([`chelabase/neon`](https://github.com/chelabase/neon)). Every local stack (`just workbench up`) starts the storage stack with the rest of its dependencies, and it backs every database.

## What runs

Docker Compose (`infra/compose/docker-compose.yml`) starts, besides the control plane's own dependencies:

- **SeaweedFS**, an S3-compatible object store, with a `neon` bucket for the safekeeper's WAL backups;
- the **storage broker**, three **safekeepers** (`safekeeper1` to `safekeeper3`, each with its WAL on its own volume), the **storage controller** (with its own Postgres) and the **pageserver**. The storage controller runs without `--dev`, which puts every timeline on three safekeepers;
- **Neon's proxy**, which terminates TLS and speaks Postgres wire and SQL over HTTP;
- **Valkey**, for the proxy's cache invalidation and query cancel, and for [realtime](/docs/architecture/realtime)'s tickets and counters;
- **NATS**, for the control plane's jobs and events and for realtime. Both NATS and Valkey require credentials (see [Security](/docs/architecture/security#service-credentials)).

The worker starts one compute container per database (and per branch) through the Docker socket, from the compute image pinned in Compose. Each compute reaches its storage through the pageserver and safekeepers, and reports to the control plane. The Neon services run as the stack's own uid, whatever the host's.

### Storage authentication

The pageserver, the safekeepers and the storage controller check a NeonJWT on their page service, WAL service and HTTP APIs. `just workbench up` derives the credentials from the stack's compute-JWT key pair: its public key as a PEM file (`compute-jwt.pub.pem`) that the three services verify with, and one scoped token per caller under `.chelabase/neon/storage-tokens/` (`pageserver-api.jwt`, `safekeeper-data.jwt`, `generations-api.jwt`, `storcon-admin.jwt`). A compute presents its tenant token; the storage controller, the pageserver and the safekeepers present the scoped ones to each other. The tokens are mode 0600 and, being Ed25519, regenerate to the same bytes.

The storage controller creates each safekeeper timeline and deletes it (local WAL and the S3 backup) with the database, branch or superseded timeline. `just storage-leak-e2e` checks that deleting reclaims the storage. The image pins and the build and bump procedure are in [`infra/neon/README.md`](https://github.com/chelabase/chelabase/blob/main/infra/neon/README.md).

## The internal listener

The orchestrator's internal listener is on `127.0.0.1:8083` (`CHELABASE_INTERNAL_ADDR`). It serves the machines that call the control plane: Neon's proxy (to look up roles and endpoints), `compute_ctl` (for each compute's spec and hooks) and the storage controller, plus the gateway, `rest` and `auth` for their lookups. Each caller has its own bearer token and can open only its own routes, and nothing goes through the gateway.

## Proxy and connections

Neon's proxy listens on port 4432 (Postgres wire) and port 4444 (WebSocket and SQL over HTTP) inside the stack's network, for hostnames of the form `<endpoint>.localtest.me`. Only the Postgres port is published on the host, as the stack's proxy port (4432 on main; see the table below), and the connection strings the control plane hands out name that host port. The serverless port is in-network only: `/connection`'s `http_url` (`https://<endpoint>.localtest.me:4444/sql`) names a port the host doesn't publish: it works only from a container on the stack's network, dialling the `proxy` service's address (as the e2e scripts do with `curl --connect-to`). `localtest.me` resolves to loopback; `CHELABASE_PROXY_DOMAIN`, `CHELABASE_PROXY_PG_PORT` and `CHELABASE_PROXY_HTTP_PORT` change the domain and the ports the control plane reports.

A self-hosted install publishes both ports (`CHELABASE_PROXY_ADDR`, default `127.0.0.1`, at `CHELABASE_PROXY_PORT`, default 5432, and `CHELABASE_PROXY_HTTP_PORT`, default 4444) and sets the control plane's domain and ports to match, so `http_url` works from the host too. The proxy takes its endpoint domain from its certificate's CN (`*.<domain>`, routing `<endpoint>.<domain>` by TLS server name); `proxy-tls` issues it for `CHELABASE_PROXY_DOMAIN` from the install's own CA. See [Install: connect to databases](/docs/self-hosting/install#connect-to-databases).

The proxy asks the orchestrator for each role's SCRAM secret. It caches role secrets for at most a minute, so a password change must publish `/password_updated` after the compute is reconfigured; `chelabase neon password-updated` does that. It fails loudly when no proxy is subscribed, rather than reporting success.

Valkey is what makes query cancel work through the proxy, and it carries the cache invalidation.

## Local ports

Each checkout's workbench stack runs in its own Docker network, and only two ports are published on the host, on loopback:

| Service | Host port (main) | Notes |
| --- | --- | --- |
| Gateway | 8000 | HTTP front door (Pingora); reaches Studio, the API and the rest by host name |
| Neon proxy | 4432 | Postgres wire (`<endpoint>.localtest.me:4432`) |

Another checkout's stack gets its own ports (gateway 8100–8199, proxy 4500–4599); `just workbench status` lists them. Everything else is internal to the stack's network and reached by service name:

| Service | Internal address | Notes |
| --- | --- | --- |
| Studio | `studio:3000` | The web app (dev server) |
| Orchestrator | `orchestrator:8081` | Management API; internal to the gateway |
| Orchestrator internal listener | `orchestrator:8083` | For the proxy, `compute_ctl`, the storage controller, the gateway, `rest` and `auth` |
| Worker health | `worker:8082` | `/health` |
| auth | `auth:8084` | Sign-in backend (via the gateway at `/auth/v1`) |
| rest | `rest:8085` | Data API engine (via the gateway at `/data/v1`) |
| rest internal | `rest:8086` | The orchestrator's schema and console calls to `rest` |
| metadata Postgres | `metadata-db:5432` | Control-plane metadata |
| NATS (with JetStream) | `nats:4222` (monitor 8222) | Provision queue, jobs and events; one credentialed user per service |
| Realtime | `realtime:8087`, `realtime:8088` | Live rows and presence: the socket and tickets (via the gateway), and `/health` |
| Identity | `identity:8080` | Accounts and sessions for members and app users; internal only, no host route ([Identity service](/docs/architecture/identity)) |
| Mailpit | `mailpit:8025` | Local email inbox (verification codes, resets) |
| Neon storage controller | `storage-controller:1234` | Tenants and timelines |
| Neon pageserver | `pageserver:9898` | Pageserver HTTP API |
| Neon safekeepers | `safekeeper1:7676`, `safekeeper2:7676`, `safekeeper3:7676` | Safekeeper HTTP APIs (WAL on 5454) |
| Neon proxy | `proxy:4432`, `proxy:4444` | Postgres wire; WebSocket and SQL over HTTP |
| Valkey | `valkey:6379` | Proxy cache invalidation and query cancel; realtime tickets and counters; ACL users only |

The storage APIs (storcon `:1234`, pageserver `:9898`, safekeepers `:7676`) require a NeonJWT, and none is published on the host. `/metrics` and the profile routes (`/profile/cpu`, `/profile/heap`) on the pageserver, the safekeepers and the storage controller need a token. `/v1/status` is public by design.

Run `just workbench psql`, `just workbench exec <service> <cmd>` and `just workbench test|run` to reach those addresses from your checkout. [`infra/compose/.env.example`](https://github.com/chelabase/chelabase/blob/main/infra/compose/.env.example) holds the documented defaults that `just workbench up` renders each stack's env file from.

## The compute network

Each stack has a `<project>_compute` network, apart from the stack's default one. Computes join only it (and `control`, the orchestrator's and test runner's path to them), never the default network. On it, besides the computes: the pageserver and the three safekeepers, which computes read and stream to; the orchestrator, whose hooks listener computes call; and the clients that dial computes (the proxy, `rest`, `auth`, the worker, the orchestrator, the test runner and realtime). Not on it: NATS, Valkey, every database container, the identity service, Mailpit, SeaweedFS, the storage broker and controller, the gateway and Studio. Every listener of a member of this network needs a credential or is public by design (health, OpenAPI); `scripts/compute-network-e2e.sh` probes each one.

`compute_ctl`'s internal server on `compute:3081` listens on loopback only and needs a per-start secret, so other computes can't reach it. Tenant storage tokens for capable computes expire after 24 hours and the worker refreshes them hourly. The orchestrator's internal listener is reached by its service name (`http://orchestrator:8083`), so no address needs to be picked per Docker flavour.

### Upgrading a stack

A stack that started before the compute network existed upgrades on its next `just workbench up`. `up` creates the new secrets (existing ones are never rewritten), renders the NATS and Valkey credential files and the storage tokens, starts `safekeeper2` and `safekeeper3`, and removes any compute that isn't on `<project>_compute`. The worker's reconcile (every 30 s) creates each removed compute again with a fresh spec; a compute's data lives in the pageserver and safekeepers, not in its container. The Neon services run as the stack's uid: the pageserver and safekeepers change the owner of an older root-owned `/data` once, on their first start.

## Checks

- `just neon-smoke` checks the storage stack alone: the safekeeper is active, the pageserver answers, and a throwaway tenant and timeline can be created, read back and deleted. It runs in the stack's runner container and needs the stack up (`just workbench up`), whose orchestrator answers the tenant's compute notification.
- `just neon-e2e` goes through the gateway API to create a test database, then proves that it answers through the proxy over Postgres wire, SQL over HTTP and the serverless driver; that a wrong password is refused; that query cancel works; and that a changed password works at once.
